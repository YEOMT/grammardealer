## 3. 지역, 적, 전투 데이터

### 3.1 테마 [확정]

대서고의 문 밖, 끝없는 밤하늘과 다른 차원으로 이어지는 야외 회랑. 압도적으로 높은 고대 기둥들이 우주로 뻗고, 오래된 돌길이 별 사이로 이어진다. 별·소원·가능성·다른 선택이라는 콘셉트를 살리되 실내 도서관·천문대·망원경 시설로 바꾸지 않는다.

입장 화면은 작은 여행자와 거대 기둥의 규모 대비, 전투 화면은 양옆 기둥과 중앙의 여백을 강조한다. 카드 뒤의 별·입자·장식을 과밀하게 만들지 않는다. 적 이름의 콘셉트를 표현하되 일반 적에 새 게임 기믹을 추가하지 않는다.

## 4. 문법 범위

다음 형태는 **지원할 대표 구조와 테스트 입력**이다. 완성문을 문자열 목록으로 화이트리스트 처리하지 않는다. 실제 어휘의 문형, 카드 사본, 형태, 절의 의존 관계로 분석한다. 대표 예문을 등록하기 위해 무관한 어휘를 대량 추가하지 않는다.

### 4.1 10-1 — 현실적인 조건절

- 기본: `If + S + 현재형, S + will/can + 동사원형`.
- 반대 순서인 `S + will/can + 동사원형 + if절`도 지원한다.
- 예시: `If I have time, I will help you.` / `If I have time, I can help you.`
- 주절은 **결과절**이다. if절이 문장 앞에 있다는 이유로 if절의 문형을 주절로 삼지 않는다.
- `if`가 명사절 연결어로 쓰이는 경우, 단순히 카드가 존재한다고 조건절 콤보를 부여하지 않는다. 현재 지원되는 기존 if 용법은 보존한다.
- 과거 사실을 조건으로 말하는 구조나 현재형끼리의 일반 조건문은 기존 분석을 보존한다. 이번 현실 조건절 콤보의 필수 신규 대상은 위의 기본 구조이며, 모든 if절에 자동 부여하지 않는다.
- 미래 조건절의 대표 규칙과 문맥상 가능한 다른 용법을 구분한다. 미지원 예외를 통과시키기 위한 임의 문법 확장은 하지 않는다.

UI 제목: **현실적인 조건절**
형태: `If + 현재형, will/can + 동사원형`
설명: **가능한 조건과 그에 따른 결과를 나타냅니다.**

### 4.2 10-2 — 가정법 과거

- 기본: `If + S + 과거형, S + would/could + 동사원형`.
- `If I had time, I would help you.` / `If I had time, I could help you.`
- 결과절 선행 순서도 동일하게 분석한다.
- `If I were happy, I would help you.` 같은 irrealis were를 허용한다. 과거형 표지를 실제 과거 사건으로 자동 해석하지 않는다.
- 교과서 대표형은 were를 제시하되 정상적인 `If she was here, ...` 유형을 표면만으로 오거부하지 않도록 검수한다. 실제 일반 과거 문맥의 be 일치 규칙까지 없애지 않는다.
- 조건절 안의 `could + 원형`도 지원 대상으로 검증한다: `If I could run, I would be happy.` 결과절의 could도 지원한다.
- could 또는 would 하나만으로 가정법을 발동하지 않는다. 실제 if 조건절과 그에 대응하는 결과절의 구조가 필요하다.
- 가정법의 `had`가 소유 동사로 쓰인 경우와 조동사 had + p.p.를 구분한다.

UI 제목: **가정법 과거**
형태: `If + 과거형, would/could + 동사원형`
설명: **현재 사실과 다르거나 실현 가능성이 낮은 상황을 가정합니다.**
상세에는 낮은 가능성의 미래 상황도 포함됨을 간단히 안내한다.

### 4.3 10-3 — 과거완료

- 유한 조동사 `had + p.p.`를 하나의 과거완료 동사구로 분석한다.
- `I had read books when she came.` / `I had helped you.`
- 일반 과거의 `I had a book.`은 과거완료가 아니다.
- 기준이 되는 과거 시점이 문맥에 있을 수 있으므로 when/before/after 카드가 없다고 had + p.p.를 자동 거부하지 않는다.
- before 등의 새 연결어는 이번 필수 신규 카드가 아니다. 실제 등록된 when과 기존 카드로 예문·실습을 구성한다.
- 가정법 과거완료의 조건절에 포함된 had + p.p.와 독립적인 실제 과거완료의 콤보 중복은 동반 채점 계약을 따른다.

UI 제목: **과거완료**
형태: `had + p.p.`
설명: **과거의 기준 시점보다 앞선 일을 나타냅니다.**

### 4.4 10-4 — 가정법 과거완료

- 기본: `If + S + had + p.p., S + would/could + have + p.p.`.
- `If she had come, I would have been happy.`
- `If I had known, I could have helped you.`
- 결과절 선행도 허용. 서로 다른 if절의 조건과 엉뚱한 주절을 묶지 않는다.
- had + p.p.만으로 가정법 과거완료를 인정하지 않는다. 두 절의 실제 연결과 형태를 함께 검증한다.
- would/could have 뒤에 has/had, 또는 동사의 일반 과거형만 오는 오류를 정상 콤보로 처리하지 않는다.
- 이 구문은 최소 두 have 사본을 사용하는 대표 경로가 있다. 한 사본을 두 위치에서 사용하는 테스트나 자동 복제는 금지한다.
- 혼합 가정법을 이번 콤보로 흡수하지 않는다. 미지원 구조를 새 비문이라고 단정하는 오류도 피한다.

UI 제목: **가정법 과거완료**
형태: `If + had + p.p., would/could have + p.p.`
설명: **과거가 달랐을 때의 상황과 결과를 가정합니다.**

### 4.5 현재완료진행 — 엔진 콤보만

- `have/has + been + -ing`를 **현재완료진행**으로 식별한다.
- `I have been reading books.` / `She has been working.`
- 독립 라운드·강제 수급·새 빙정 묶음은 추가하지 않는다. 사용 후 콤보와 도감에서 이름·형태·설명을 표시한다.
- `I have been happy.`는 현재완료진행이 아니다. `The book has been read.`도 현재완료진행이 아니라 기존 완료/수동 경로다.
- `had been -ing`, `will have been -ing` 등을 현재완료진행으로 오분류하지 않는다. 이들의 기존 지원 여부를 유지하되 이번 신규 완료진행 배율을 자동 부여하지 않는다.
- 상태동사의 진행형 등 기존 어휘별 제약을 제거하지 않는다. 시간 부사/기간 표현을 반드시 추가해야 성립하도록 강제하지 않는다.
- 현재완료·진행과 동일 근거에 배율을 중복 지급하지 않는다. 분석용 하위 특징과 채점용 근거를 분리한다.

### 4.6 형태와 문법 역할의 분리

보조동사 연결은 현재 구조를 확장해 구현한다. 조건의 시제·상·법을 분리하고, 텍스트의 단순 포함 여부나 첫 동사만으로 태그를 정하지 않는다.

- 시간의 골렘 등 기존 시제 기믹에도 가정형의 형태상 과거를 실제 과거 사건의 증거로 무조건 전달하지 않도록 회귀 검사한다. 구버전 원정의 기존 해석은 해당 버전으로 보존한다.
- `will` 형태는 실제 will 사용, `would` 형태는 선택된 would 사용이다. 카드의 lemma가 will이라는 이유로 would에 미래 콤보를 주지 않는다.
- can/could 뒤에는 원형을 검증한다. could에는 과거 능력·가능성 등 여러 쓰임이 있으므로 모든 could를 과거시제 또는 가정법으로 단정하지 않는다.
- `I could read when I was young.`과 실제 if 가정법의 could를 구별한다. 단독 `I could help you.`는 조건절이 없으므로 가정법 콤보/예견 우회 대상이 아니다.
- 토큰 순서를 바꿔도 같은 구조는 같은 주절·콤보가 나온다. 쉼표는 표시용이며 쉼표 카드나 문장부호를 문법의 유일한 근거로 요구하지 않는다.
- 문법과 의미상의 어색함을 분리한다. 게임은 주어진 시제 형태로 현실의 참/거짓을 판정하는 시스템이 아니다.

## 5. 카드 DB·형태 선택·획득

### 5.1 카드 정책 [확정]

| 카드 | 정책 | 형태 |
|---|---|---|
| `will` | 기존 ID·고급·사본·강화 유지, 형태 확장 | will / would |
| `can` | 신규 고급(UNCOMMON) WORD·조동사 카드, 시작 덱 제외 | can / could |
| `if` | 기존 고급 연결어 재사용 | if |
| `have` | 기존 희귀·활용·시작 덱 정책 유지 | have / has / had 및 기존 등록형 |
| `be` 및 내용 동사 | 기존 데이터·활용 유지 | were / been / p.p. / -ing 등을 재사용 |

would/could를 별도 영구 카드 정의로 만들지 않는다. 조동사 카드에 명사 can 같은 다른 품사나 wills/cans/coulds/ing/pp를 자동 생성하지 않는다. can의 기본 점수·연마·카드 크기는 기존 WORD 체계를 따른다. 신규 특별효과는 없다.

형태 메뉴는 기존 조립대의 형태 변경 조작을 확장한다. 선택 상태가 원정·전투 컨텍스트와 함께 일관되게 해석되어야 한다. UI 이름만 바꾸고 실제 snapshot에는 will/can을 남기는 오류를 금지한다.

### 5.2 해금/보상 시점 [구현 세부안]

- 신규 can은 **Stage 10 입장 상점과 10-1부터의 전투 보상**에서 정당한 후보가 될 수 있어야 한다. 보스 클리어 후에만 해금하는 순환 의존을 금지한다.
- 기존 if/will/have의 앞선 획득 경로는 줄이지 않는다. Stage 10 관련 슬롯에서 이 카드들이 후보가 되는지 검사한다.
- 보상 3칸 중 1선택, 기존 고급/희귀 가중치와 가격·중복 처리·선택 취소·저장 후 후보 고정을 유지한다. 반드시 can이 나오는 확정 슬롯이나 무료 희귀 have를 추가하지 않는다.
- 새 if 조건/가정/과거완료 콤보의 해금은 새 원정의 Stage 10 진입에 연결하는 것을 기본으로 한다. 문법 분석 자체와 해금된 점수는 분리한다.
- 현재완료진행은 독립 지역 학습을 요구하지 않는다. **새 버전에서 기존 완료와 진행 콤보가 모두 해금되면** 추가 조건 없이 채점할 수 있는 것을 기본으로 한다. 기존 원정의 점수 정책은 바꾸지 않는다.
- would는 새 버전 will의 등록형으로 제공한다. Stage 10 이전 실제 문장이 성립하면 정상 분석을 보존하되, 미해금 가정법 콤보를 주지 않는다. 새 can의 보상 해금 시점은 위 정책을 따른다.

## 6. Stage 10 일반전의 조건부 빙정

### 6.1 최소 사본 보충표

| 전투 | 필요 최소 영구 사본 수 기준 |
|---|---|
| 10-1 | if 1, will 1 |
| 10-2 | if 1, will 1, can 1 |
| 10-3 | have 1 |
| 10-4 | if 1, will 1, have 2 |
| 10-5 | **없음. 모든 경우 0장** |

각 항목의 지급 수는 `max(0, 최소 수 - 영구 활성 덱의 해당 cardDefId 사본 수)`로 산출한다. 현재 손패/조합대/선택한 형태로 소유 여부를 판단하지 않는다. 임시 빙정이나 제거된 사본의 기록도 보유 수에 포함하지 않는다.

예: 10-4에 have가 0/1/2/3장 있으면 have 빙정은 각각 2/1/0/0장이다. will이 would로 선택되어 있어도 will 사본으로 센다. 10-4의 can 추가 지급은 합의되지 않았으므로 하지 않는다. could 경로는 이미 획득한 can으로 활용할 수 있다.

### 6.2 수명과 정산

전투 생성 시 1회만 지급한다. 사용하면 다시 지급하지 않는다. 매 턴 손패가 부족할 때 덱을 자동 복구하지 않는다.

빙정은 영구 활성 덱·보상 소유·상점 판매 대상으로 추가하지 않고 기존 임시 사본 테이블과 전투 ID에 연결한다. 공격 제출이 정상 접수되어 턴·카드가 소비되면 성공 여부와 무관하게 제출한 빙정 사본은 소멸한다. 엔진 오류/미접수는 소멸·턴 소비가 없다. 교환은 기존 임시 WORD 규칙을 따르고, 소멸한 사본을 재활용/셔플로 부활시키지 않는다.

승리·패배·지역 이동 시 사용하지 않은 사본까지 전부 정리한다. 10-4에서 남은 빙정이 직조자전으로 넘어가지 않는다. 저장·불러오기·전투 시작 중복 요청으로 지급 수가 늘지 않는다.

### 6.3 초반 가시성 [검증 초깃값]

기존의 기본 문장 보정 손패를 보존하면서, 해당 전투에 지급된 목표 재료 중 최소 1장을 첫 손패에서 접하도록 기존 안정적 교환 방식을 재사용한다. 기본 문장 재료나 손패 한도에 충돌하면 임의 카드 생성/강제 제거 대신 가시성 미확보 사유를 기록한다. 지급이 0장이면 추가 조정하지 않는다.

모든 재료를 첫 손패에 몰아주거나 정답 조합 전체를 보장하지 않는다. can/will/have를 어느 순서로 볼 수 있는지 실제 드로우 검증 결과를 보고한다. 빙정 가시성 때문에 보상·상점 RNG를 소비하지 않는다.

### 6.4 보스전 무지원 [최우선 확정]

10-5에서 if/will/can/have/be 등 목표 문법 재료, 무료 운영 카드, 영구 보충, 보스 전용 목표문장 보정을 지급하지 않는다. 새 `create...Frost` 경로는 10-5에서 명시적으로 지원 0으로 종료한다.

일반적인 보유 덱 기반 첫 손패 보정, 보유 룬의 손패 효과, 원래 보유한 운영 카드는 기존 규칙대로 작동한다. 이것들을 제거하는 의미가 아니다. 이 규칙은 기존 Stage 6 사슴·Stage 8·Stage 9 공급 정의를 소급해서 바꾸는 전역 규칙이 아니다.

입장 안내: **일반전에서는 부족한 핵심 재료를 빙정으로 지원합니다. 운명의 직조자전에는 지급되지 않으니, 상점과 카드 보상으로 덱을 준비하세요.**

## 7. 운명의 직조자 — 예견

### 7.1 확정 공략 문구

> 직조자는 직전 공격의 주절 문형을 기억합니다.
> 같은 문형으로 다시 공격하면 피해를 줄 수 없습니다.
> 가정법 공격은 예견을 무시합니다.

HP **5000**. 첫 유효 공격에는 기억이 없다. 일반 몬스터 저항은 적용하지 않는다. 추가 피해 감소·회복·HP1 보호·페이즈·강제 2회 이상 타격 조건을 넣지 않는다.

### 7.2 문형과 가정법 근거

비교 키는 정규화된 **SV / SVC / SVO / SVOO / SVOC** 중 하나다. be 위치문 등 기존 학교 문형 매핑을 재사용하고, SVC의 명사/형용사 보어는 같은 SVC로 센다. 내용절 목적어를 가진 SVO도 같은 SVO다. 한 문장의 종속절/관계절에 다른 문형이 있다는 이유로 주절 문형을 바꾸지 않는다.

문두 if절이 있는 문장은 **결과절의 문형**으로 비교한다. 일반 조건문·일반 과거완료·현재완료진행·단독 would/could는 자동 예외가 아니다.

예견 무시는 정상 **if 가정법 과거 또는 if 가정법 과거완료**의 구조 근거가 있고, 그 결과절이 이번 공격의 주절에 실제 연결될 때만 인정한다. 임의로 포함된 종속절의 would/could, 잘못된 조동사형, 미지원 혼합 가정법은 우회 근거가 아니다. 단어의 철자가 아니라 분석 결과를 사용한다.

### 7.3 유효 공격과 상태 전이 [구현 세부안]

1. 제출 snapshot과 문법 분석을 확정하고 기존 규칙으로 저항/예견 전 공격력을 계산한다.
2. 정상적인 주절 필수 성분과 1~5형식 근거가 없는 `INVALID_CORE`, 미지원·엔진 오류·구조 실패·예견 전 0점은 새 기억을 만들지 않는다. 경미한 감점이 있는 `VALID_WITH_ISSUES`는 상태 이름만으로 통째로 배제하지 말고, **주절 구조 자체가 정상인지**와 실제 양수 채점 여부로 판단한다. 복구된 가짜/불완전 주절로 기억을 돌려서는 안 된다.
3. 유효 공격이고 가정법 근거가 유효하면 예견을 우회한다.
4. 그렇지 않고 이전 기억과 주절 키가 같으면 해당 공격의 최종 피해를 **0**으로 만든다.
5. 이전 기억과 다르거나 이전 기억이 없으면 기존 계산 피해를 준다.
6. 유효한 공격은 그 주절 문형을 새 기억으로 남긴다. 가정법 우회 공격도 포함한다. 예견으로 막힌 공격은 같은 문형을 다시 기억하므로 변화가 없다.
7. HP가 0이면 즉시 승리한다. 마지막 턴도 승리가 우선이다.

준비·교환·카드 배치·형태 변경·정렬·모달·룬 재정렬·운영 카드 사용은 기억을 지우거나 바꾸지 않는다. 구조적으로 실패한 문장을 일부러 내어 기억을 초기화할 수 없다. 새 전투에서는 기억을 초기화한다.

가정법 콤보가 유효하지 않은데도 우회만 허용하는 이중 판정 경로를 만들지 않는다. 분석이 모호하면 더 높은 점수나 유리한 보스 결과를 기준으로 해석을 고르지 않는다.

### 7.4 정산과 UI

순수 보스 판정에서 `rememberedFrameBefore/After`, `bypassed`, `blocked`, `attackId`, `preBossPower`, `finalPower` 및 문법 근거를 반환하고 Controller에서 1회 커밋한다. 기존 필드명에 맞춰 이름을 조정할 수 있다.

시작 상태: **예견: 없음**. 공격 후: **예견: 3형식**처럼 실제 기억만 표시한다.
동일 문형 차단: **예견에 읽혔습니다 · 피해 0**.
가정법 우회: **가정법 · 예견 무시**.

지금 조립 중인 문장의 주절/가정법/예상 피해를 제출 전에 예측 표시하지 않는다. 확정된 보스 기억을 보여주는 것은 허용한다. 0 피해의 이유를 문법 오류로 오표시하지 않는다.

`FINISH_PRESENTATION`, watchdog, 반복 콜백, 같은 명령 재전송은 HP·기억·턴·보상을 다시 정산하지 않는다. 저장과 진행 중 연출 복원 정책은 기존 안전 저장 규칙을 따른다. 공격 직전/직후 근거를 보고서와 테스트에서 확인한다.

## 8. 콤보 및 후반 일반전 저항

**정확한 배율과 저항은 `02_BALANCE_AND_SCORING_KO.md`의 검증 초깃값을 적용한다.** 필수 배율은 현실 조건절 ×1.6, 가정법 과거 ×1.8, 과거완료 ×1.4, 가정법 과거완료 ×2.0, 현재완료진행 ×1.8이다.

같은 동사구/절 연결에 겹친 완료·진행·일반 과거·가정법·절 연결 근거를 그대로 전부 곱하지 않는다. 반면 별개의 관계절/수동/다른 동사구에서 성립한 기존 콤보까지 전역 차단하지 않는다.

지역 보너스는 현실 조건절·가정법 과거·과거완료·가정법 과거완료 중 실제로 유효하고 해금된 대상이 있을 때 **×1.25, 공격당 한 번**. 라운드 소개와 별개로 Stage 10 전체의 동일 대상 집합을 쓴다. 현재완료진행은 엔진 콤보이지만 **그 자체만으로 Stage 10 지역 보너스를 주지 않는 것을 구현 기본값**으로 한다.

새 원정의 Stage 7/8/9/10 **일반 몬스터만** 30/35/40/30% 저항. 모든 계산이 끝난 공격력에 최종 1회 적용한다. 보스와 이전 저장에는 추가하지 않는다.

## 9. 입장 상점·보상·47전투 경계

### 9.1 Stage 9에서 진입

새 원정은 Stage 9 도서관장 승리→기존 보상 정산→Stage 9 클리어→Stage 10 소개→입장 상점→10-1 순서로 진행한다. 보상 건너뛰기도 정상 경로다. 재접속/저장으로 이 과정에서 중복 지급하지 않는다.

현재 0.9는 Stage 9/42전투에서 종료된다. 새 기능 뷰로 확장하되 구버전의 종료 계약은 그대로 둔다.

### 9.2 Stage 10 상점

기존 짝수 지역 상점을 재사용해 다섯 번째 입장 상점을 만든다. 별도의 시스템·추가 화폐·무료 신상품을 도입하지 않는다.

**구현 기본값**: 기존 후반 상점과 동일하게 룬 2칸·카드 3칸(기존 운영 카드 전용 칸 포함), 기존 연마/제거 서비스의 이용 횟수·가격·가격 상승을 재사용한다. 새로운 추가 서비스는 없다. 재고·선택·가격·RNG를 저장 시 고정한다.

상점 열림 전에 해당 원정의 can 등 신규 보상 해금 정보를 적용한다. 상점 표시용 최소 entry receipt는 사용할 수 있지만, 기존 영구 지급 함수를 복사해 공략용 can/will/have를 무료 추가해서는 안 된다.

### 9.3 종료

10-5 승리→기존 지역 보스 보상 1회 정산→`CONTENT_COMPLETE / STAGE10_END`로 정상 종료한다. 실제 전투 수는 **47**이다.

문구: **별의 회랑을 통과했습니다. 이번 버전의 여정은 여기까지입니다.**

최종 스토리 클리어·승천·50전투 완료·48번째 전투 진입·최종전 상점/보상/엔딩 버튼을 활성화하지 않는다. 앞으로 48~50번째 전투를 만들기 위한 ID 공간만 남길 수 있다. 더미 적을 생성하여 50으로 숫자를 맞추지 않는다.

## 10. 저장·버전·카드 보존

0.10.0 새 원정만 Stage 10, 새 배율 정책, 후반 일반전 저항을 사용한다. 0.9 이하 진행·완료 원정은 기존 카드 정의·형태·콤보·보상 확률·저항 없음·종료 경계를 재현한다. 0.9 완료 세이브를 자동 연장하지 않는다.

새 버전 번호의 누락으로 0.9 기능이 후퇴하지 않도록 중앙 capability/registry/score/rune/reward/shop/temporary/save/tutorial/guide 선택기를 전부 대조한다. 문자열 `>=` 비교로 0.10과 0.9를 비교하지 않는다. 같은 코드 상수를 전역 변경해 과거 원정에 적용하지 않는다.

물리 카드 ID, 영구/임시/소멸 파티션, 강화 수준, 룬 레벨·순서, 저장 슬롯, 원정 seed, 공개된 offer/shop, 이전 보스 완료 기록을 유지한다. 새 can/형태 ID가 해당 버전 manifest와 저장 검사에 등록되어야 한다. 최초 상점·첫 전투 시작·보상 확정·완료에서 안전 저장을 검증한다.

0.9의 help 제외/보상 전용, have 시작 덱 정책, 희귀도, 다이아몬드 확률을 단순 버전 분기 누락으로 잃는 회귀를 특히 검사한다. 시작 덱의 장수·품사 비율은 바꾸지 않는다.

## 11. 학습 UI·도감·자산·접근성

기존의 짧은 제목·형태·한 줄 설명·실제 지역 보너스 구조를 유지한다. 공격 중 점수/피드백을 보여주고 다음 편집 단계에 학습 안내를 복귀시킨다. 설명문이 공격 연출을 조기에 덮지 않는다.

현재완료진행을 포함한 5개 신규 콤보 이름과 will/would·can/could의 의미 차이를 상세에 표시한다. p.p.는 과거분사라는 짧은 설명을 제공한다. 외형만 바꾸지 말고 실제 사용한 형태·역할이 사후 기록과 일치하도록 한다.

고급 can의 테두리, 형태 메뉴, 카드 점수, 품사색은 기존 WORD 규칙을 적용한다. 일반 저항 라벨은 학습 제목과 분리한다. 빙정의 긴 설명을 손패에 다시 넣지 않는다. 도움말은 터치/클릭 가능하고 hover 전용이 아니다.

첫 입장 후 자동으로 긴 설명을 연속 팝업하지 않는다. 기존 학습코스 기능이 있다면 대응 항목을 추가하고, 설명용 테스트 덱과 실제 원정 덱/보상은 분리한다. 새 강제 튜토리얼 원정을 만들지 않는다.

기존 최소 화면·데스크톱·터치에서 카드 선택/드래그/교환/메뉴/보상/상점/점수 연출을 점검한다. 배경 자산이 없거나 로드 실패해도 UI가 사라지거나 진행이 막히면 안 된다.
