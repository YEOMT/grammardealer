# 센텐스 발라트로 0.3.0 — 시간의 협곡 대형 업데이트
## Codex 통합 구현 명세 · 최신 main 보존형

> 정확한 문장을 만들면 강해지고, 카드와 룬을 잘 구성하면 크게 폭발한다.
> 게임은 영어 문법의 성립 여부와 게임 콤보의 해금을 분리한다.
> 시간의 골렘은 예고된 과거 → 현재 → 미래의 세 부위를 순서대로 공략하는 특별한 보스다.

- 작성일: 2026-10-05, Asia/Seoul.
- 목표 버전: **0.3.0**. 새 원정으로 Stage 1~3, **총 12 전투**를 플레이한다.
- 코드 기준: 작업 착수 시점 `YEOMT/grammardealer`의 최신 `origin/main`.
- 조사 시 확인한 기준: `d6535b6c8c74132a34e7eb56f778ef0eedcd3b24` (0.2.2 PR #4 병합).
- 위 SHA는 조사 기록이다. 이후 main의 정상 변경을 버리고 이 SHA로 되돌리라는 뜻이 아니다.
- 작업 브랜치 권장: `codex/v0.3-time-canyon`.
- 이 문서는 **구현 지시와 기대 결과**다. 구현 완료·실행 테스트 통과 보고가 아니다.
- 이 문서의 새 필드·파일명은 최소 구조 제안이다. 같은 책임의 기존 모듈을 우선 재사용한다.
- Markdown 본문만으로 작업 가능하다. 동봉 JSON은 기대값 보조 자료이며 완성 코드·통과 결과가 아니다.

## 0. 착수·보존·작업 방식

1. 루트와 수정 경로의 `AGENTS.md`, `README.md`, `docs/PROJECT_HANDOFF.md`, `docs/ARCHITECTURE.md`, `docs/LANGUAGE_SCOPE.md`, 0.2.1/0.2.2 패치·검증 문서를 먼저 읽는다. 이전 문서의 시점별 수치와 이번 변경을 섞지 않는다.
2. 현재 경로·Git 저장소·branch·dirty 상태를 확인한다. `git fetch origin` 후 최신 main과 차이를 확인하고 별도 브랜치에서 작업한다. 사용자 미커밋 작업을 삭제하거나 강제 reset/clean하지 않는다. 이미 같은 작업이 진행 중이면 진행 기록을 읽고 이어 간다.
3. 소스가 실제 0.2.2(고정 실습·무효 제출 정산·문법/콤보 분리·사전/도감 정비)를 포함하는지 확인한다. 버전 문자열만 믿지 않는다. 과거 Work ZIP·배포 번들·다른 DS 게임으로 소스를 대체하지 않는다.
4. Vanilla JS + ES Modules + Vite를 유지한다. React·상태관리 프레임워크·서버·외부 AI·번역 API·대형 NLP 모델·새 게임 엔진을 도입하지 않는다.
5. **실제 구현 → 관련 검사 → 통합 → 최종 검증 → 빌드 → PR**까지 진행한다. 문서 요약, 하드코딩한 정답 데모, Stage 3 버튼만 추가한 상태를 완료로 보고하지 않는다.
6. 정상 기능은 보존하고 이번에 명시한 규칙만 변경한다. 불필요한 폴더 재구성·전체 Parser 재작성·일괄 코드 포맷 변경을 피한다.
7. 완료 후 작업 브랜치를 push하고 main 대상 PR을 생성한다. main 직접 push·자동 merge·Pages 설정 변경·승인 없는 공개 배포는 하지 않는다.
8. 구현 중에는 관련 테스트를 우선한다. 무거운 덱/원정/전체 브라우저 검사를 매 CSS 수정마다 반복하지 않는다. 다만 최종 제출은 `AGENTS.md`가 요구하는 test/build 및 이번 변경의 실제 회귀 검사를 충족한다.
9. 이미 결정된 사항을 다시 기획 질문으로 돌리지 않는다. 미결정 세부값은 아래 `테스트 초깃값`으로 구현하되 조정 근거를 남긴다. 실제 충돌·환경 제약이 있으면 완료한 부분과 남은 부분을 구분한다.

| 시간 콤보 | 과거 계열 ×1.2, 진행형 ×1.3, 완료형 ×1.4, will 미래 ×1.2. 각 계열 공격당 한 번 |

## 2. 보존 범위와 명시적 제외

### 보존

- 여행자, 어휘 초급/기본/심화/자유와 게임 난이도의 분리. 이번 공개 난이도는 기존 1만 유지.
- 시작 **28장**, 첫 손패 6, 손패 한도 10, 턴당 3장, 교환 4회, 전투 6행동, 조합대 16장. 합법적인 기존 운영 룬 효과.
- 클릭/드래그 조립, 카드 회수/재배열/맞교환, 별도 형태 메뉴, 먼저 체크 후 버리기, 편집 Undo.
- 0.2.1의 필수 첫 실습: 고정 카드·실제 두 공격·교환·준비·형태 선택·확인 gate·정상 덱/RNG 복원. 실습을 끝낸 프로필의 재강제 없음.
- 0.2.2 일반 전투: 비어 있지 않은 조합의 확정, 핵심 실패 0 피해+카드/턴 소비, 부분 오류 감점, 기술 실패 무소모.
- 문법 판정과 콤보 해금 분리. 원정 시작 해금 snapshot + 원정 자체 해금만 자격에 사용.
- develop SV/SVO, 여러 Sense 탐색, 기존 1~4형식 및 제한된 목적격보어/to/원형/관계절 기본 판정.
- 혼합 3칸 중 1선택, 첫 룬 선택, 대상 선택 취소 시 보상 고정, 재화·제거·연마·토파즈/장막.
- 초원 **77/132/242**, 항구 **220/300/380/640**. 기존 구버전 원정에는 해당 구버전 HP.
- 느린 읽기용 점수 연쇄, 보석색 룬 효과, 0.2.1의 hit-stop·전투판 반동·감쇠·효과 감소.
- 개인 프로필·영구 해금·과거 문장 기록·수동 3슬롯·동일 로컬 DB·난수 재현·정산 멱등성.

### 이번에 하지 않는다

비교급/최상급/as~as, can/must/should 등 조동사 대량 추가, would·가정법, 새 부사절/that 명사절, 명령/의문/부정문 대형 Pack, Stage 4~10 실전 콘텐츠, 관계절·준동사의 새 전용 콤보, 희귀 룬 대개편, Lv3 특수 특성, 새 캐릭터/승천/랭킹/Firebase/PWA, 완성 이미지·BGM 생성.

수동태·분사 수식·동명사 Pack 전체는 후속이다. 새 p.p. 카드를 보고 어떤 배열이든 완료로 위장해서 인정하지 않는다. 기본 판정이 아직 없는 드문 구조는 실제 범위 제한으로 명시하고 내부 진단한다. 아래 필수 12형 및 기존 지원 구조를 이 핑계로 빼면 안 된다.

‘시간의 협곡’과 비교 표현 이동을 로드맵에 반영한다. 비교의 최종 배치 지역은 이번에 새로 확정하지 않는다. 기존 Stage 6의 완료 첫 소개는 과거완료 등 시간 관계 확장으로 추후 조정할 메모만 남긴다.

## 4. 전체 진행·해금·종료

### 4.1 실제 12 전투

- Stage 1: 전투1~3, 현재 0.2.1 실습 및 자유 전투 정책 유지.
- Stage 2: 전투4~7, 입장 후 기존 첫 상점, 항구 4형식 장막.
- Stage 3: 전투8~12, 새 지역 소개·골렘 예고·필수 카드 지급·첫 전투. **상점 없음**.
- Stage 3 보스 최종 처치 → 일반적인 지역 보스 보상 → **시간의 협곡 완료 / 0.3 제공 구간 완료**.
- 전체48전투 스토리 완료/난이도 해금/다회차 보스 해금과 혼동하지 않는다.
- Stage 4는 미구현. ‘다음 지역’이나 방문 불가능한 상점 버튼을 만들지 않는다.

### 4.2 원정 상태

`BATTLE → REWARD → BETWEEN_BATTLES`는 유지한다.
지역 마지막 보상 이후는 지역 정의/원정 manifest로 판단한다.

- Stage 1 끝: `STAGE_CLEAR → STAGE_INTRO(stage.02) → ENTER_STAGE → SHOP → BATTLE`.
- Stage 2 끝(새 0.3): `STAGE_CLEAR → STAGE_INTRO(stage.03) → ENTER_STAGE(입장 지급) → BATTLE`.
- Stage 3 끝: 마지막 보상 해결 후 `CONTENT_COMPLETE`, `STAGE3_END`.
- 구 0.2.x 원정: 여전히 `STAGE2_END`. 새 콘텐츠로 몰래 확장하지 않는다.

지역 이름·배경·카운터·적/보스 kind·보상·도감 stageLabel은 데이터에서 읽는다. Stage 3를 항구로 표시하거나 세 번째 일반 전투을 보스로 간주하지 않는다.

### 4.3 시간 콤보의 영구 해금

Stage 2 보스 최종 승리를 확정하는 시점에 `STAGE2_CLEAR`를 한 번 발행한다. 현재 구간종료에 의존한 이벤트를 그대로 두어 Stage 3 진입 시 누락되지 않게 한다.

- `pack.time.past`, `pack.time.progressive`, `pack.time.perfect`, `pack.time.futureWill`(이름 제안)을 원정/프로필에 함께 한 번 부여.
- 같은 보스 보상의 후보 생성 전에 해금을 반영하고, 이미 생성된 보상은 바꾸지 않는다.
- 네 효과는 동시에 열되 Stage 3 일반 전투의 초점은 과거/진행/완료/미래 순으로 안내한다.
- 이미 Stage 2를 완료한 기존 프로필은 `stage2CompletedRunIds` 등 확실한 실적에서 새 해금 자격을 한 번 보완할 수 있다. 단순 파일버전·최근 접속·highest 값 추측만으로 성공 실적을 발명하지 않는다.
- 이전 원정 시작 snapshot은 새 프로필 해금으로 재작성하지 않는다. 새 원정에서만 새 기준을 사용한다.
- 새 0.3의 모든 지원 형태/구조는 Stage 1부터 기본 판정 가능하다. 미해금이면 시간 전용 점수만 없다. 파서나 형태 메뉴를 Stage 3 입장 조건으로 완전히 잠그지 않는다.

### 4.4 슬롯 로드맵

기존 합의의 ‘Stage 3 클리어 후 4 슬롯’을 새 0.3 원정의 완료 보상으로 연결한다. 초기 및 Stage 3 전투 중에는 3 슬롯, Stage 3 최종 승리 후 보상부터4슬롯이다. 새 원정은 다시3슬롯.
6스테이지 이후5슬롯은 metadata만 유지하며 지금 활성화하지 않는다.
구버전 원정은3슬롯 그대로. 룬 검증은 무조건전역3이 아니라 해당 원정의 합법 slotLimit를 확인한다.

| 지역전투 | 전체번호 | 이름 | 기본표시 | 초점 | HP 초깃값 |
|---|---:|---|---|---|---:|
| 3-1 |8|고대의 거북이|🐢|과거|320|
| 3-2 |9|질주하는 토끼|🐇|진행|360|
| 3-3 |10|사냥을 완료한 늑대|🐺|현재완료|400|
| 3-4 |11|미래를 보는 독수리|🦅|will 미래|440|

지역은 협곡의 바위·바람·시간 문양을 기존 CSS/asset 슬롯으로 표현한다. 이미지 파일이 없어도 fallback으로 정상 작동하게 한다. 새 이미지나 음악을 받아야 진행 가능한 상태를 만들지 않는다.

각 일반 전투 소개는 한 줄 중심:
- 과거: ‘동사 형태를 바꾸어 지나간 일을 표현해 보세요.’
- 진행: ‘be와 -ing형을 연결해 진행 중인 일을 표현해 보세요.’
- 현재완료: ‘have/has와 과거분사를 연결해 현재와 이어지는 경험·상태를 표현해 보세요.’
- 미래: ‘will 뒤에 동사원형을 연결해 앞으로의 일을 표현해 보세요.’

완료 늑대의 사냥 이미지를 ‘현재완료는 항상 끝난 일’이라는 규칙으로 설명하지 않는다. 긴 문법 강의·퀴즈·정답 문장 강제 없이 소개를 닫고 일반 전투를 자유롭게 진행한다.

### 지역보너스

Stage 3의 네 시간 효과 중 최소 하나가 정상적으로 성립하고 해당 효과 자격이 있으면 **×1.25 한 번**.
현재형만으로 공격하는 것도 가능하나 일반현재 자체에는 별도 시간 지역보너스가 없다.
‘이번 전투 중점: 현재완료’와 ‘시간 표현 지역보너스 ×1.25’를 구분해, 다른 시간형을 써도 보너스를 받는 규칙을 숨기지 않는다.
골렘의 현재 부위는 일반현재도 공격 가능하며, 그것이 자동 지역보너스를 뜻하지는 않는다.
한 문장에 과거/진행/완료/미래가 여럿 있어도 지역 배수는 한 번이다.

## 6. 필수 카드 공급·기본 덱·신규 카드

### 6.1 Stage 3 입장 지급

보스 예고를 본 뒤, 첫 전투 셔플 전에 현재 `activeCardIds` 및 실제 인스턴스로 be/have/will 보유를 검사한다.

- 없는 Lexeme 카드만 각각 한 장 지급. 최대3장.
- 손패에 없다고 지급하지 않는다. DRAW/DISCARD에 있어도 보유다.
- 이전에 제거한 카드가 사전에만 남은 것은 보유가 아니다.
- 이미 가진 연마/희귀/기본 사본을 대체하지 않는다.
- 한 입장당 `entryGrantId`로 한 번. 재열기·로드·같은 명령 중복은 추가 지급 없음.
- 이후 학생이 제거하면 자동 복구하지 않는다. 다음 부위에 필요한 카드도 자동 생성하지 않는다.
- 보관 덱·실습 덱을 혼동하지 않는다. 실제 원정 소유권만 변경.
- 표시: 없는 카드가 덱으로 들어가는 짧은 연출. 이미 다 있으면 ‘시간을 다룰 재료가 준비되어 있습니다.’ 한 줄.
- 입력/렌더 중단 후에도 지급된 카드·사전·RNG·trace가 정확히 한 번 반영되게 한다.

### 6.2 be/have의 두 역할

be는 주동사/진행 보조동사로, have는 소유 주동사/완료 보조동사로 같은 카드가 쓰인다. 카드 하나가 두 위치를 동시에 차지하지 못한다.
`I have had a book.`은 have 카드가 **두 장**, `I am being kind.`는 be 카드가 **두 장** 필요하다.
`I will have been running.`은 I/will/have/be/run 다섯 장이다. been은 be, running은 run의 선택 상태.

### 6.3 will과 시간 부사

- 필수 신규 Lexeme/Card는 **will 하나**를 기본안으로 한다. 현재 최신 registry에 이미 있으면 중복 ID를 만들지 않는다.
- will은 조동사 역할, 고급(테스트값), 기본10, 형태는 will만. 임의 wills/willed/would 생성 금지.
- 새 0.3 일반 보상·상점 후보로는 초반부터 등장 가능. 28장 시작 덱의 일반 VERB 역할 슬롯에는 넣지 않는다.
- 사전의 한국어 요약은 ‘~할 것이다 · 뒤에 동사원형’ 정도. 문장 자동번역 없음.
- 기존 `now`, `today`는 새 동사구와 정상 결합을 검사한다. `recently`는 준비된 기존 Lexeme의 실제 용법/위치/과거·완료 결합을 검수해 0.3 보상 후보로 활성화할 수 있다. 새 단어를 무더기로 추가하지 않는다.
- yesterday/tomorrow/for/since/시간 숫자 등을 보스 공략 필수로 만들지 않는다. 시간 부사가 없어도 동사구가 성립하면 인정한다.
- 늑대 때문에 hunt/finish, 독수리 때문에 fly/win을 필수 단어로 추가하지 않는다. 예문과 테스트는 실제 공급 카드로 구성한다.

### 6.4 덱 생성의 공정성과 재현

초기28장 품사·동사역할·첫패 정책은 유지한다. 기능어 will이 일반 SV 동사 슬롯을 차지하거나, auxiliary have가 소유 SVO 경로를 빼앗지 않게 한다.
새 형태/가산성 감사가 generation witness를 바꿀 수 있으나, 레거시 덱 생성·RNG는 정확히 보존한다. 가능하면 새 0.3 물리 시작 덱도 기존 역할 표본을 유지하고 새 판정으로 재검증한다.
동사구를 많이 쓰게 된 만큼 ‘모든 드로우가 답을 주는 보정’으로 해결하지 않는다. be/have/will의 한 번 공급과 일반 보상 기회, 4회 교환을 활용한다.

## 7. 동사 형태 DB — 준비된 형태의 활성화와 과거분사 보완

### 7.2 형태 UI

- 메뉴를 `현재/기본`, `과거`, `과거분사·p.p.`, `-ing`로 보기 쉽게 구분.
- be 기본표시는 계속 be. was/were는 각각 주어와 일치 규칙을 가진다.
- 새 0.3에서 지원하는 형태는 처음부터 선택 가능하되 기본 현재형을 우선 배치한다. Stage 3에서만 ‘형태 선택지가 늘어났음’을 짧게 소개한다. 모든 형태 선택을 정답 자동교정으로 만들지 않는다.
- 1024×768 터치에서 메뉴가 화면 아래 잘리거나 hand scroll과 충돌하지 않게 한다.

### 7.3 같은 철자, 다른 역할

played/had/read/run처럼 철자가 같은 형태는 내부적으로 구별하되 **숨은 formId만으로 올바른 표면 문장을 오답으로 만들지 않는다**.
- `I have played.`: 메뉴에서 played의 ‘과거’를 눌렀어도 표면과 문맥이 p.p.로 성립하면 정상 완료.
- `I have run.`: run이 원형과 같은 철자여도 정상 p.p. 가능.
- `I read a book.`: 현재/과거가 모두 가능한 경우, 사용자가 명시적으로 선택한 현재/과거 형태를 정상 후보 간의 해석 고정 정보로 사용한다. 기본 선택은 현재. 보스 약점이나 높은 점수에 맞춰 엔진이 몰래 해석을 변경하지 않는다.
- read의 현재/과거 선택은 메뉴와 제출 기록에서 구분할 수 있어야 한다. 둘을 동시에 시간 증거로 적립하지 않는다.
- `I have went.`처럼 표면 자체가 요구 형태가 아니면 오류다. went를 gone으로 조용히 바꾸지 않는다.
- 복수 분석은 실제 정상 후보 중 정규화 한 번. 카드수·콤보 중복 계산 금지.

## 8. 동사구·시제 판정 계약

### 8.1 Parser를 새로 쓰지 말고 주동사 판별 앞뒤를 확장

보조동사 순서와 완료·진행 결합은 24절 [LANG-1]~[LANG-5]를 참고한다.

현재 NP/AP/PP·여러 Sense·관계절·비정형절 조립을 유지하면서, 절의 동사 자리에서 auxiliary chain을 읽는다.

기본 능동 연쇄:
`[will] → [완료 HAVE] → [진행 BE] → lexical verb`

- will 뒤 요소는 원형.
- 완료 HAVE가 요구하는 다음 동사는 과거분사.
- 진행 BE가 요구하는 다음 본동사는 -ing.
- 유한동사(첫 be/have 또는 단독 본동사)가 주어와 시제·수·인칭 관계를 갖는다. will은 인칭 변화 없음.
- 목적어·보어·문형은 **마지막 본동사의 Sense/Frame**으로 판정한다. 조동사 be가 있다고 무조건2형식, have가 있다고 무조건3형식이 아니다.
- 보조동사도 실제 사용한 카드로 기본 점수를 받되 별개의 절·주절 문형으로 중복 계산하지 않는다.

### 8.2 필수 지원12형 — 각 행은 실제 규칙 판정

| 구조 | 카드 예 | 시간 계열 | 추가 특징 |
|---|---|---|---|
| 현재 | I play games. | PRESENT | 단순 |
| 과거 | I played games. | PAST | 단순 |
| 현재진행 | I am playing games. | PRESENT | PROGRESSIVE |
| 과거진행 | I was playing games. | PAST | PROGRESSIVE |
| 현재완료 | I have played games. | PRESENT | PERFECT |
| 과거완료 | I had played games. | PAST | PERFECT |
| 현재완료진행 | I have been playing games. | PRESENT | PERFECT, PROGRESSIVE |
| 과거완료진행 | I had been playing games. | PAST | PERFECT, PROGRESSIVE |
| will 미래 | I will play games. | FUTURE | WILL |
| 미래진행 | I will be playing games. | FUTURE | WILL, PROGRESSIVE |
| 미래완료 | I will have played games. | FUTURE | WILL, PERFECT |
| 미래완료진행 | I will have been playing games. | FUTURE | WILL, PERFECT, PROGRESSIVE |

과거완료에 두 번째 과거절이 없다고 자동 오류로 만들지 않는다. 현재완료에 for/since/ever가 없다고 반려하지 않는다. 미래형에 tomorrow가 없어도 정상이다. 이번 게임은 대화 밖 문맥을 추측해 시제 적절성 감점을 하지 않는다.

`will have played`를 현재완료로, `have played`의 played만 보고 과거로, `will be playing`의 be만 보고 현재로 분류하지 않는다.
미래 계열은 이번 게임에서 will 구성을 중심으로 정의한다. 이를 ‘영어의 미래는 반드시 will뿐’이라는 일반 문법 지식으로 설명하지 않는다.

### 8.3 주절과 내포절

위 동사구 분석을 기존 지원 관계절에도 재사용한다. 같은 구문이 주절에서는 성공하고 관계절에서는 복수 동사 오류가 나면 실패다.
- `I like the book that she made.`: 현재 주절 + 과거 관계절.
- `I liked the book that she will read.`: 과거 주절 + 미래 관계절.
- `I will read the book that she made.`: 미래 주절 + 과거 관계절.
- `I have read the book they made.`: 현재완료 주절 + 목적격 생략 과거 관계절.

비정형 to절 안의 have/been/pp는 문장 성립을 위한 VP 합성을 지원하되 **독립적인 유한 시간 증거로 만들지 않는다**.
`I want to have read the book.`을 `had read`처럼 과거 부위의 열쇠로 삼으면 안 된다.
16장·현재 관계절 깊이 등 기존 bounded 원칙 유지. 강제 정답 문자열 목록, 무작위 단어 재배열 탐색, API 판정 금지.

### 8.4 분석 결과에 남길 증거

필드명 예시(기존 계약에 맞게 배치 가능):

```text
verbPhrase: {
  clauseId, verbPhraseId, cardIds,
  finiteCardId, lexicalVerbCardId,
  auxiliaryRoles, tenseFamily: PAST|PRESENT|FUTURE,
  aspects: [PERFECT, PROGRESSIVE], futureMarker: WILL|null,
  chainWellFormed, temporalEvidenceEligible,
  issueIds, sourceSpan
}
```

- 한 절은 하나의 temporal family. 한 문장은 여러 절의 family를 포함할 수 있음.
- 실제 동사구 범위 전체를 V로 표시하고, 필요할 때 보조동사·본동사를 세부 표시한다.
- `I have given my friend a book.`은 주절4형식, V=have given, IO=my friend, DO=a book.
- `I will be happy.`는2형식, `I was running.`은1형식.
- 렌더러가 영어 문자열을 다시 split/정규식 판정해 역할이나 시간 계열을 만들지 않는다.

### 8.5 오류·회복

사용자 확정 정책대로 일반 전투는 모든 비어 있지 않은 합법 입력을 제출한다.

- `He have played games.`, `They was running.`: 정상 골격·시간 계열은 명확하고 일치 오류만 있음. 기존 일치 감점, 완전한 문장 보너스 없음. 시간 증거는 사용할 수 있다.
- `He will runs.`, `I have went.`: 연결은 알아볼 수 있으면 명시적인 형태 오류로 회복할 수 있으나 완전한 문장 보너스 없음. 잘못된 링크에 의존한 시간 콤보/골렘 열쇠는 부여하지 않는다. 실제 카드는 바꾸지 않는다.
- `I running.`, `I will.`, `I have been.` 등 주동사/필수 성분이 없는 핵심 실패:0 피해, 카드/턴 소모.
- `I be happy.`의 기존 형태 미선택은 부분감점으로 유지. 원형 be만 보고 CURRENT 열쇠를 만들어 주지 않는다.
- 본문 관사 하나가 틀렸어도 별도로 정확한 시간 동사구까지 무효로 만들지는 않는다.
- 오류 중복은 causeId/실제 원인 기준으로 막는다. 같은 보조동사형 하나 때문에 -10을 세 번 부과하지 않는다.
- 새 형태 링크 감점은 **-10**을 기본안으로 하며 기존 수치표와 함께 관리한다.

실제 한도 초과·데이터 손상·계산 예외는 학생의 문법 실패가 아니다. 자원은 보존하고 최소한의 복구만 알린다. 내부 `UNSUPPORTED`를 무조건 VALID로 치환하지 않는다. 필수 지원12형이 이 경로로 빠지면 미완료다.

### 8.6 학교문법상 주의점

진행형이 제한되는 상태 의미를 동사 표면 전체에 ‘절대 불가’로 하드코딩하지 않는다. have의 소유/활동, be의 상태/행동 등 실제 Sense 차이가 있다. 실제 검수 가능한 용법 설명을 사전에 한 줄 제공하고, 문맥으로만 판단할 부분에 새로운 의미 감점을 추가하지 않는다.
대표 학습/보스 검증 문장은 play/run/work/help 등 안전한 동작 용법을 사용한다. 문제가 있는 문장을 자동 생성 예문으로 ‘정확한 영어’라고 추천하지 않는다.

## 9. 시간 콤보·점수 계산

### 9.1 기존 수치 변경 — 새 0.3 원정에 적용

| 항목 | 새 수치 |
|---|---:|
| 카드 기본 점수 |10 유지|
| 연마 |단계당+5, 최대3 유지|
| 완전한 문장 |+30|
| SV |13/10|
| SVC(형용사/명사 보어) |8/5|
| SVO |9/5|
| SVOO |11/5|
| 기본 수식·PP·기존 감점 |기존값 유지|
| 지역 |5/4, 공격당1회|

`수정 룬`의 +20/+35/+50은 그대로다. **완전한 문장 보너스 +30과 수정 룬 +20을 혼동해 수정 룬까지 +30으로 바꾸지 않는다.**

### 9.2 시간 콤보(새 테스트 초깃값)

| 계열 | 효과 | 표시 예 |
|---|---:|---|
| PAST |×6/5|과거 계열! ×1.2|
| PROGRESSIVE |×13/10|진행형! ×1.3|
| PERFECT |×7/5|완료형! ×1.4|
| FUTURE_WILL |×6/5|will 미래! ×1.2|

공격당 각 계열 최대1회. 서로 다른 계열은 실제 구조가 있으면 함께 발동한다.
- had played: 과거+완료.
- will have been playing: 진행+완료+미래. 현재·과거 보너스 없음.
- 과거절3개: 과거 계열은 한 번. 동일 p.p.를 과거+완료로 잘못 이중 분류하지 않는다.
- 일반현재는 별도 시간 콤보 없음. 원래 문형/룬은 정상 적용.
- 미래완료 등 복합형 이름을 표시할 수 있지만 ‘미래완료 추가×2’ 같은 다섯 번째 보너스는 만들지 않는다.

고정 순서:
`카드/연마 → 정확성 감점·제외 → 완전한 문장 → 주절 문형 → 시간(PAST→PROGRESSIVE→PERFECT→FUTURE) → 기존 수식/PP → 룬 위→아래 → 지역 → 보스 → 최종위력`.
새 시간 이벤트 순서를 데이터로 고정하고 UI 재렌더/해금/보스에 따라 바꾸지 않는다. 배수는 정수 유리수, **각 곱셈 직후 내림**.

### 9.3 실제 증거와 자격

Grammar는 시간 family·aspect를 처음부터 분석한다. ComboEligibility가 pack 해금을 읽고 해당 이벤트를 고른다.
미해금 시간형은 완전한 문장과 실제 기본 문형·수식·허용 룬으로 정상 공격하지만 전용 시간 배수는 없다. `미지원`, `다음 지역에서 사용 가능` 등으로 제출을 막지 않는다.
0.2.2에서 검증된 관계절/to/목적격보어는 계속 판정하되 새 전용 보너스는 이번에 추가하지 않는다. Grammar가 낸 원본 증거와 이번에 점수화한 hit IDs를 둘 다 기록한다.

### 9.4 시간 보스는 필터된 점수 증거만 보지 않는다

현재 resolveEncounter 호출은 eligibleAnalysis를 전달한다. 골렘 열쇠는 **원본 분석의 검증된 temporal evidence**를 읽어야 한다.
문법 성립, combo 해금, enemy 규칙은 서로 다른 책임이다. 정상 시간형인데 특정 콤보가 잠겨 있다는 이유로 열쇠가 사라지거나, 점수 없는 일반현재가 CURRENT 부위를 공격하지 못하면 안 된다.

## 10. 기존 룬 상향과 신규 운석 룬

### 10.1 확정 상향

| 룬 | Lv1 | Lv2 | Lv3 |
|---|---:|---:|---:|
| 루비·사파이어·에메랄드 |1.6|2.2|2.8|
| 토파즈 |1.7|2.4|3.2|
| 호박 |1.4|1.8|2.4|

효과 조건·희귀도·기존 ID·중복획득 레벨업은 유지. 수정/비취/철·금빛/옥/구리 수치는 이번에 바꾸지 않는다.

### 10.2 운석 룬 기본 정의

- 새 이름/등급/상위레벨은 설계자 기본안: **운석 룬 · 고급**, `rune.longSentence`.
- 정상적으로 구조/역할이 인정되어 점수에 기여하는 **물리적 단어 카드 수**를 센다.
- Lv1: 1~4장 효과없음, 5~9장×2, 10~16장×3.
- Lv2: 5~9장×2.25, 10장 이상×3.5.
- Lv3: 5~9장×2.5, 10장 이상×4.
- 해당 슬롯에서 가장 높은 구간 한 번만 발동. 10장에서×2×3=×6 금지.
- 같은 단어의 다른 카드 사본은 각각 센다. as 두 장도 두 장, have와been도 별도 물리 카드.
- orphan/unlicensed 카드, 문장 밖 손패, 철자 길이, 노드 중복, 표시용 문장부호를 세지 않는다.
- 부분 오류가 있으나 문장 뼈대가 성립하면 기존 감점 후 룬 발동 가능. 운석을 몰래 ‘완전무결해야만 발동’으로 강화하지 않는다.
- 핵심 실패는 모든 룬과 무관하게0. 16장 엉터리 배열에 ×3을 주지 않는다.
- 부사가 정상적으로 반복 사용되면 길이에 포함한다. 별도 very 억제 규칙·장문 일반 감점은 추가하지 않는다.
- 시작부터 해금된 새 0.3 후보로 하되 firstRuneBasicPoolEligible=false. 최초 고정 수정/호박/구리 후보는 유지. 이후 첫 룬의 BASIC2칸에는 제외, 전체 구현풀1칸에는 등장 가능.
- 기존 룬12종(11+운석)만 실제 활성. 미래 시간 룬·관계절 룬·희귀 대개편은 활성화하지 않는다.
- 신규고급룬의 상점 가격은 기존 고급 룬 24를 재사용한다. 배율이 세다는 이유로 숨은 희귀 잠금·출현0 설정을 추가하지 않는다.

### 10.3 UI

설명 예: ‘사용 카드 5장 이상 ×2 / 10장 이상 ×3 · 높은 구간 한 번’.
발동 시 인정 카드가 짧게 함께 반응하고 `운석 룬 · 10장 이상 ×3`를 표시한다. 문장 편집 중 실제 카드를 분석해 조건 충족 체크·예상점수를 띄우지는 않는다.
룬 레벨 메뉴와 보상 설명은 실제 levelValues에서 표시하고, 고정 텍스트가 수치와 어긋나지 않게 한다.

## 11. 룬 순서 UX — 기존 명령 재사용

- 오른쪽 패널에 ‘위에서 아래로 발동’을 잘 보이게 표시.
- 각 룬에 순서번호·▲▼ 직접 버튼을 제공. 첫/마지막 이동 금지 상태를 정확히 표시.
- 드래그 핸들에서 Pointer Events 기반 세로 재배열, 삽입선/자리 표시. 모달을 열어야만 순서를 바꿀 수 있는 기존 UX를 개선한다.
- 모바일 터치/키보드에서도 ▲▼로 동일 기능 가능. 드래그가 취소되면 원래 순서, 커밋·RNG·자원 변화 없음.
- 실제 순서 변경은 기존 `REORDER_RUNES`에 새 순서의 인스턴스ID 배열을 전달한다. 장착 배열을 DOM에서 직접 바꾸지 않는다.
- 편집 중 또는 허용된 전투 밖에서만 변경. 공격 확정 후 연출/gate/보상 거래 모달 중에는 잠금.
- 순서 변경은 턴/교환/카드/재화 소모 없음. 이미 계산된 공격 기록은 변경 없음.
- 금빛/옥/구리의 전투시작 규칙 snapshot을 재계산·재지급하지 않는다.
- 상점에서 순서를 바꿀 수 있는 최소 룬 관리 보기를 제공하되 상품 구성을 늘리지 않는다.
- 룬 설명 클릭·▲▼·드래그의 이벤트 전파를 분리해 한 행동이 두 번 실행되지 않게 한다.

## 12. 시간의 골렘 — 3단계 전투 계약

### 12.1 특별한 예외

일반 적·항구 보스는 높은 위력으로 원킬 가능한 기존 철학을 유지한다.
**시간의 골렘만** 최초 스토리에서도 순차 필수 시간 공략을 갖는다. 최소3제출이 필요함을 지역 입장 때 예고한다. 다른 보스에 공통 최소공격수/전역 피해 상한을 만들지 않는다.

### 12.2 상태 기본안

```text
bossMechanic: {
  id: TIME_GOLEM,
  activePhase: 0,
  phaseOrder: [PAST, PRESENT, FUTURE],
  phases: [
    {id: PAST, maxHp: 240, hp: 240, broken: false},
    {id: PRESENT, maxHp: 240, hp: 240, broken: false},
    {id: FUTURE, maxHp: 240, hp: 240, broken: false}
  ]
}
```

전체hp = 세 phase hp 합. 전체maxHp = 세 maxHp 합.
이미 부순 앞 단계는hp0/broken, 뒤 잠금 단계는maxHp 그대로. 허가되지 않은 부분손상·역순·건너뛰기 저장을 거절한다. 실제 최종 파괴 뒤에만 defeated와승리를 기록한다.

### 12.3 시간 열쇠

활성 부위에 해당하는 **정상적으로 형성된 유한절의 temporal evidence가 문장 어디든 최소 하나** 있으면 통과한다. 주절뿐 아니라 기존 지원 관계절도 포함한다.

| 부위 | 인정 |
|---|---|
| 과거의 갑옷 | PAST: 일반과거/과거진행/과거완료/과거완료진행 |
| 현재의 엔진 | PRESENT: 일반현재/현재진행/현재완료/현재완료진행 |
| 미래의 신경 | FUTURE: will미래/미래진행/미래완료/미래완료진행 |

- PP에 ‘과거’라는 뜻의 단어, p.p. 카드 하나, will이라는 문자열만으로 인정하지 않는다.
- I have games는 have 소유의 일반현재이고 완료가 아니다. I had games는 과거이지만 완료는 아니다.
- I have played는 현재완료이므로 past 열쇠가 없다.
- I will have played는 future, 현재완료도 과거도 아니다.
- 정상 시간구조에 관사 오류 등 별도 작은 오류가 있어도 열쇠는 인정. 시간링크 자체가 틀렸거나 유한형을 지정하지 않았다면 그 증거는 열쇠에서 제외.
- 한 문장이 과거+현재+미래를 모두 포함해도 **활성 단계 하나만** 공격한다. 다음제출 없이 다음 단계를 공격하지 않는다.

### 12.4 정산 순서

1. 공격 시작의 enemy/activePhase/revision을 snapshot으로 고정한다.
2. 실제 문법·기본 점수·콤보·룬·지역을 계산한다.
3. 고정된 활성 부위의 열쇠 충족 여부를 원본 temporal evidence로 확인한다.
4. 불충족: preBossScore는 기록하고 finalPower/actualHpLoss=0, phase 변화없음. 카드/턴은 소모.
5. 충족: finalPower는 원래 계산된 큰 위력을 유지한다. `actualHpLoss = min(finalPower, activePhase.hpBefore)`.
6. 해당 phase hp와 전체hp에서 actualHpLoss만 뺀다. 다음phase hp는 건드리지 않는다.
7. 현재phase hp0이면 phaseBreak event를 한 번 생성하고 activePhase를 하나만 전진한다. 다음 단계에서 같은 공격을 재적용하는 while loop 금지.
8. 세 번째phase까지 깨졌을 때만 killed=true. 그 전에는 지역보상/재화/스토리승리 없음.
9. 마지막 행동에서 세 번째phase를 파괴하면 승리가 턴소진보다 우선. 앞부분만 깨고 턴0이면 파괴 연출 후 패배.

### 12.5 숫자 의미

`preBossScore`, `finalPower`, `actualHpLoss`, `phaseExcess`, `enemyHpBefore/After`, `bossStateBefore/After`, `phaseBreak`를 구분한다.
예: 활성phase 잔여240에 위력600 → actualHpLoss240, phaseExcess360, 다음부위는240 그대로.
최종 피해표시는 ‘위력600 / 적용피해240 · 부위 파괴’처럼 구분할 수 있다. 갑옷 한 구간에 많이 넣었다고 전체 보스를 죽인 것처럼 표시하지 않는다.

구간 초과는 다음턴에도 저장되는 버프·충전·재화가 아니다. 기존 전체적 overkill 필드를 부위 초과와 혼용하지 말고 정의를 유지하거나 명시적으로 버전분리한다.

### 12.6 실제 시도 비용·원인 분리

- 불완전한 문장:0점, 기존 문법실패 안내, 카드/턴 소비, phase 변화없음.
- 정상 문장이나 시간불일치: 점수 연쇄는 실제로 진행, 보스가 방어하여 피해0, 카드/턴 소비.
- 완전한 문장 여부와 ‘이번 적에 피해를 주었음’을 같은 조건으로 저장하지 않는다.
- 기술 실패: 커밋 이전 모든 제안 원복, 카드/턴/HP/phase/RNG/통계 보존.
- doubleclick/commandId/revision/attackId/FINISH 재호출로 두 번 소비하거나 두 구간을 깨지 않게 한다.

### 3분할 HP

왼쪽 과거/중앙 현재/오른쪽 미래를 독립체력 막대로 표시한다. active는 밝게, 미래구간은 잠금, 완료구간은 파괴표시. 색만으로 구분하지 말고 텍스트·아이콘을 함께 둔다.
- 과거: 모래시계/깨진시계.
- 현재: 맥동하는엔진.
- 미래: 별/빛의신경망.
각 부위 hp/maxHp와 현재필요계열을 읽을 수 있게 한다. 화면 폭이 줄어도 문구/숫자 겹침없음.

### 시간 불일치 고정 문구

- ‘공격이 막혔습니다! 과거의 갑옷을 깨려면 과거 계열 문장이 필요합니다.’
- ‘공격이 막혔습니다! 현재의 엔진을 멈추려면 현재 계열 문장이 필요합니다.’
- ‘공격이 막혔습니다! 미래의 신경을 끊으려면 미래 표현이 필요합니다.’

작은 보충: 현재는 일반현재/현재진행/현재완료, 과거는 과거진행·완료 포함, 미래는 will 진행·완료 포함.
문법이 틀렸다는 빨간오답과 혼동하지 않게 방어 피드백으로 구분한다.

### 사용자 확정 파괴 문구

- **과거의 갑옷이 부서집니다!**
- **현재의 엔진이 멈춥니다!**
- **미래의 신경이 끊어집니다!**

계산은Controller에 한 번 커밋하지만 보이는 HP/phase는 실제 충돌 때 바뀐다. 읽기용 점수 계산 중 미래구간으로 화면이 먼저 넘어가지 않게 한다.
첫째/둘째 파괴 때 보스 전체를 사라지게 하지 않는다. 각갑옷/엔진/신경망 층만 바뀌고 다음부위가 드러난다. 세 번째에서만 전체 퇴장.

기존 hit-stop·충격음·반동 사용. 같은 physics/RNG 없이 CSS/Canvas/DOM으로 작은 국소 파편을 재사용한다. strong tier는 큰 계산위력과 해당부위 기준체급에 따라 상한을 두고 연출하며 실제 피해가0이면 타격/처치연출 금지.

임팩트·phaseBreak 애니메이션이 끝나기 전에 finish가 모두 cancel해 파괴가 안 보이지 않게 한다. hidden/abort/timeout은 표시를 커밋된 최종state로 안전하게 수렴. 화면 재생이 턴/phase를 추가 변화시키지 않는다.

## 14. 보상·경제·공략 준비

보상 확률은 **선택지 한 칸 기준**이며 기존과 동일하다.

| 종류 | 일반 전투 | 지역 보스 |
|---|---:|---:|
| 일반 카드 |50%|0%|
| 고급 카드 |10%|10%|
| 희귀 카드 |5%|10%|
| 연마 |15%|25%|
| 제거 |10%|5%|
| 룬 |10%|50%|

항상 혼합된 세 칸 중 하나를 선택한다. 중복·실행 불가능한 서비스·최대 레벨 룬을 배제하는 정책과 첫 룬 특례는 유지한다.
Stage 3의 지역 관련 후보에는 be/have/will, 동작 동사·주어·목적어 등 공략을 준비할 기회를 제공한다. 이를 이유로 매번 현재 덱을 정답 덱으로 자동 수리하지 않는다.

- 기본 승리 재화는 일반 적 +2, 지역 보스 +6, 남은 턴당 +1이다. 건너뛰기 재화도 유지한다.
- 상점 수·가격·강화 1회·제거 1회를 유지한다. Stage 3에 임시 상점이나 보스 직전 무료 정비소를 추가하지 않는다.
- 골렘의 앞 두 부위를 파괴했을 때는 승리 재화가 없다. 세 부위를 모두 파괴한 뒤에만 보스 재화와 남은 턴 보너스를 정산한다.
- Stage 3 완료 뒤 4슬롯이 되면 마지막 보상에서 합법적으로 룬을 장착할 수 있다. 미래 지역까지 개방하는 것은 아니다.
- 운석이나 버프로 기존 적을 원킬하면 정상적인 고점으로 인정한다. 자동으로 적 HP를 올려 상쇄하지 않는다.

### 실제 6행동 안에서 검증한다

골렘은 세 단계를 강제한다. 모든 부위를 두 번씩 공격해야 겨우 잡히는 체력을 기본값으로 삼으면 준비할 턴이 사라진다.
**보통 수준으로 강화한 덱은 ‘공격 4회 + 준비 2회’ 또는 ‘공격 5회 + 준비 1회’ 같은 경로로, 고점 빌드는 공격 세 번으로 공략할 수 있게 하는 것**이 목표다. 공격과 준비를 합쳐 6행동을 넘기는 경로를 성공 사례로 세지 않는다.

이것은 같은 카드를 매 턴 주는 합성 산술이 아니다. 실제 시작 28장에 보상·입장 카드가 합쳐진 덱, 교환 4회, 현재 손패와 셔플을 사용해 검증한다.
공략이 불합리하게 어려우면 순차 턴 설계, 보상 기회, 동사·주어 밀도, will 접근성, 새 적 HP 순으로 원인을 확인한다. 새 골렘의 구간 HP를 낮춰 조정할 수는 있지만, 전투 턴을 몰래 늘리거나 부위가 바뀔 때 정답 카드를 생성하지 않는다.

## 15. 도감·사전·명사 가산성

### 15.1 문장 도감 시각 위계

`처음 완성 문장`, `최고 완성 문장`, `최근 제출`의 영어 원문을 별도 요소와 클래스로 분리한다.

- 영어 원문: 밝은 흰색(예: `#F5F7FA`), 굵기 700~800, 현재보다 약 10~15% 크게. 18~20px를 시작값으로 보고 실제 레이아웃에 맞춘다. 줄 간격은 1.45 이상을 권장한다.
- 제목·횟수·위력 등 보조 정보: 기존의 보조 회색을 유지한다. 영어 원문과 같은 줄에 붙여 전부 굵게 처리하지 않는다.
- 오류·조언: 은은한 붉은색(예: `#F0A0A5`)과 ‘피드백’ 레이블 또는 아이콘을 함께 사용한다. 일반 문법 설명까지 붉게 표시하지 않는다.
- 자동 정답 추천·영문 수정·문장/단어 번역·내부 `VALID`, `UNSUPPORTED`, capability 표시는 다시 넣지 않는다.
- 11~16장으로 만든 긴 문장을 정상적으로 줄바꿈한다. 가로 태블릿과 화면 확대 상태에서도 내용이 잘리거나 겹치면 안 된다.

### 15.2 고정 학습 예문 영역 제거

학생 도감의 `고정 학습 예문 · 실전 기록 아님` 버튼·펼침 영역·내용을 렌더하지 않는다.
검수한 예문 데이터, `grammarGuideData`, 자동 테스트 fixture는 보존한다. 고정 예문을 플레이어의 기록으로 옮기거나 사용 횟수를 만들지 않는다.
기존 펼침 영역에 함께 들어 있던 IO/DO나 위치 be 설명은 필요한 한 줄만 일반 문법 설명으로 유지한다. 예문 영역을 제거하면서 중요한 문법 설명까지 무심코 삭제하지 않는다.

### 15.3 한국어 뜻은 단어 사전에 남긴다

나의 덱에는 단어 뜻·형태·보유 장수·연마·간단한 검수 용법을 유지한다. 새 p.p., -ing형과 가산성 안내도 실제 데이터에 맞춰 표시한다.
손패 앞면에 한국어 뜻을 항상 넣거나, 문장 도감의 툴팁에 번역을 되살리지는 않는다.

### 15.4 technology 오감점 수정

용법 근거: 24절 [LANG-6], [LANG-7].

특정 기술을 뜻하는 COUNT 용법과 일반 기술을 뜻하는 MASS 용법을 모두 지원한다. 현재 MASS-only 정책 때문에 발생하는 `a technology` 감점을 제거한다.

- `a technology`, `a very easy technology`, `technologies`, 한정사 없는 `technology`를 각각 합법적인 용법으로 분석한다.
- technology를 단순히 COUNT-only로 바꾸지 않는다.
- 기존 Sense에 가산성별 후보를 추가하거나 COUNT/MASS/BOTH를 도입하되, **명사구마다 하나의 해석과 수**를 확정한다.
- a/an이 있으면 단수 가산 후보, 복수 형태이면 복수 가산 후보, 한정사 없는 단수형 technology는 불가산 후보를 사용할 수 있다.
- BOTH라는 이유로 `a technologies`나 수 불일치를 통과시키지 않는다.

사용자 피드백 문장:

> I am a very easy technology they help on strong ideas.

이 문장을 실제로 분석하여 technology의 가산성만을 이유로 감점하지 않게 한다. 다른 문법 문제가 발견되면 독립적인 근거로 구분한다. 사용자 문장이므로 전체를 무조건 정답 처리하는 하드코딩도, 의미가 기묘하므로 감점하는 처리도 금지한다.

### 15.5 활성 명사 전수 감사

`docs/NOUN_COUNTABILITY_AUDIT_0.3.md`에 실제 명사 전체, 기존 정책, 채택한 COUNT/MASS 용법, 대표 예, 형태, 변경 근거를 기록한다.
technology/culture/time/food/room처럼 용법에 따라 가산성이 달라지는 단어를 검토한다. information/homework 등에서 학교문법의 대표 불가산 규칙을 무작정 해제하지 않는다. 특수한 문맥의 모든 용법을 한 번에 구현하는 것은 아니다.
복수형이 추가되면 같은 카드의 형태로 제공한다. 이를 이유로 새 단어 카드, 시작 장수, 가격을 몰래 변경하지 않는다.

### 15.6 과거 기록

이전 기록의 당시 위력·집계·승리·해금은 보존한다. 토큰 증거가 있으면 현재 교육 규칙으로 읽기 전용 재검토를 하고, 지금은 오류가 아닌 관사 피드백을 현행 규칙처럼 반복 노출하지 않는다.

|---|---|---:|
| I be happy. |(30−10)×1.6 → ×1.25|**40**|
| He runs very fast. |(40+30)×1.3 +5+5 → ×1.25|**126**|

첫 공격 후 적은 77→37로 생존하고, 두 번째 공격으로 격파된다. 두 공격과 한 번의 준비를 사용하므로 남은 턴은 3이다. 기본 승리 2 + 턴 보너스 3 = 재화 5라는 흐름도 유지한다.

확인 gate의 숫자는 고정된 30/87이 아니라 해당 `AttackResolution`의 실제 이벤트값에서 읽는다. 둘째 공격은 카드 40 → 완전문장 70 → 문형 91 → 수식 101 → 지역 126이다.
구 0.2.1/0.2.2 실습 저장은 원래 30/87을 유지한다. 숫자만 바뀌었다는 이유로 이미 실습을 마친 프로필에 강제 재실습을 요구하지 않는다. **실습 완료 계약과 사용한 점수표 버전을 분리**한다.
사용자 확인·hidden 시간의 watchdog 제외, stale ACK·중복 FINISH·재시작·나가기·실습 덱 복원은 기존 검사와 함께 검증한다.

## 17. 저장·버전·출시 호환

### 17.1 작은 버전별 설정으로 처리

새 원정은 game `0.3.0`, manifest `campaign.0.3`, Stage 1~3의 12전투를 사용한다.
기존 0.1.0/0.1.1/0.2.0/0.2.1/0.2.2 원정은 원래 언어·콤보·점수·룬·HP·공개 후보·상품·난수·완료 경계를 유지한다.

전역 `SCORE_BALANCE`와 `RUNE_BY_ID`만 바꾸면 구버전 원정의 다음 공격까지 달라진다. 원정의 `contentVersions`로 선택하는 작은 수치·룬·언어·전투 정의 resolver 또는 확정 snapshot을 사용한다.
매 버전마다 전체 엔진을 복사하지 않는다. 공유 알고리즘과 버전별 데이터를 사용하고, 기존 레거시 view를 보존한다.

### 17.2 새 저장 상태

- Stage 3 입장 여부, entryGrant, 지급한 인스턴스 ID, 해금 milestone.
- 실제 지역 진행과 종료 경계, 적 정의와 전체 HP.
- 골렘 activePhase, 각 부위 hp/maxHp/broken, 처리한 phaseBreak 증거.
- 동사 형태 선택, 조합대 snapshot, 원정에 동결된 시간 콤보 자격.
- 운석 룬·레벨·장착 순서·합법적인 slotLimit.
- 고정 보상·상품·가격·서비스 사용 여부, 네 가지 RNG 스트림.
- 공격의 시간 증거·점수 타임라인·부위 before/after·위력·실제 피해·구간 초과.

### 17.3 안전 지점

기존 안전 지점과 0.2.2의 빈 조합대 턴 경계를 유지한다. 골렘의 한 부위를 파괴한 뒤에도 연출이 끝난 합법적인 턴 경계라면 저장할 수 있다.
연출·설명 gate·카드 드래그·거래 모달 도중에는 저장하지 않는다. 새로운 중간 자동 저장 시스템을 추가하지 않는다.
로드는 보스 초기화·재셔플·입장 카드 재지급·상점 재추첨을 하지 않는다. 같은 합법 명령을 이어서 실행하면 같은 결과가 나와야 한다.

### 17.4 프로필

기존 로컬 DB 이름, 수동 3슬롯, playerId와 표시명 분리를 유지한다.
`STAGE3_CLEAR`를 한 원정에서 한 번 기록하고 최고 완료 지역은 3까지 갱신한다. 전체 48전투를 마치기 전에는 `storyClearCount`를 증가시키지 않는다.
영구 해금은 새 원정의 선택지를 넓히는 효과다. 룬을 무료로 지급하거나 레벨을 올리지 않는다.
최고 위력은 계산된 finalPower를, 누적 실제 피해는 actualHpLoss를 사용한다. phaseExcess를 누적 피해·처치 재화에 더하지 않는다.

## 19. 교육 문구·출처·검수 산출물

`docs/VERB_MORPHOLOGY_AUDIT_0.3.md`, `docs/NOUN_COUNTABILITY_AUDIT_0.3.md`, `docs/EDUCATION_REVIEW_0.3.md`를 작성한다.
변경한 형태·가산성·문법 규칙과 확인한 출처를 연결한다. 사전의 일부 의미를 단어 전체의 절대 규칙으로 확대하지 않는다.
자동 번역이나 즉석 문법 설명을 생성하지 않고, 검토 가능한 고정 데이터만 학생에게 제공한다. AI가 출처를 확인한 상태를 ‘교사 검수 완료’라고 표현하지 않는다.

권장하는 짧은 설명:
- 과거: ‘과거의 일을 나타낼 때 동사의 과거형을 사용합니다.’
- 진행: ‘be + -ing형으로 진행 중인 일을 나타낼 수 있습니다.’
- 완료: ‘have + 과거분사로 기준 시점과 이어지는 경험·상태·결과 등을 나타낼 수 있습니다.’
- 미래: ‘will 뒤에 동사원형을 연결해 미래의 일을 표현할 수 있습니다.’
- p.p.: ‘과거분사는 과거형과 다를 수 있습니다.’
- 골렘 현재 부위: ‘일반현재·현재진행·현재완료 등 현재 계열 문장으로 공격하세요.’

설명은 짧게 유지한다. 모든 시제 용법과 언어학적 분류 논쟁까지 도감에 넣지 않는다.

## 21. 테스트 운영과 실제 플레이 검증

### 21.1 불필요한 반복은 줄이되 최종 검사는 생략하지 않는다

개발 중에는 관련 unit/fixture부터 실행한다. 소스가 안정된 뒤 전체 필수 test/build와 영향받는 브라우저 검사를 실행한다.
이번에는 언어·가산성·후보·버전·진행이 바뀌므로 최종 10,000개 덱 검사를 한 번 수행한다. 작은 색상 변경마다 같은 대량 검사를 반복할 필요는 없다.

현재 명령을 먼저 확인한다: `npm test`, `npm run validate:data`, `npm run build`, `npm run test:decks`, `npm run test:runs`, `npm run test:browser`, `npm run test:e2e`.
새 명령은 필요할 때만 추가하고 README에 설명한다. 마지막 검사 후 소스를 다시 변경했다면 영향받는 검사와 AGENTS 필수 검사를 다시 수행한다.

### 21.2 자동 검사

- 어휘 네 모드 × 2,500시드 = 10,000개 시작 덱·첫 손패. 기존 검사와 레거시 golden을 재사용한다.
- be/have/will의 여덟 가지 보유 조합에서 0~3장 입장 지급과 중복 방지.
- 시간 공략을 이해하는 실제 명령 정책으로 최소 네 모드 × 20시드 = 80원정. 일반현재만 반복하는 정책으로 골렘의 정상 난도를 평가하지 않는다.
- 완주·정상 패배·기술 실패를 모두 기록한다. 미래 카드 접근 실패, 준비 턴 수, 부위별 공격 수, 전투별 최고 위력, 원킬, 보상/제거 선택을 추적한다.
- 자동 정책은 현재 손패와 공개된 정보만 사용한다. 카드 주입·HP 수정·미래 드로우 열람·엔진 밖 점수 산출로 결과를 꾸미지 않는다.
- 실제 여섯 행동 안에서 세 시간 계열을 공략하는 경로와, 준비가 부족해 실패하는 경로를 모두 남긴다. 선별한 성공 시연을 사람의 일반 승률이라고 보고하지 않는다.

### 21.3 브라우저

최소 1366×768, 1440×900, 1024×768 가로 터치, 1280×800을 확인한다.

- 새 프로필의 실습 40/126, 완료 프로필의 강제 재실습 부재.
- 도감 원문의 흰색·굵기·크기, 적색 피드백, 고정 예문 영역 부재, 번역/내부 상태값 부재.
- 룬 ▲▼·드래그·키보드·스크롤 취소·저장된 순서.
- 긴 문장·확장 손패·불규칙형·p.p. 형태 메뉴와 역할 범위.
- 골렘 세 체력바·방어·구간 초과·마지막 턴 승패·단계 복원.
- 효과 감소·음소거·설명 장기 대기·탭 전환·fast-forward 회귀.
- 실제 iPad/Safari/Android를 사용하지 않았으면 NOT RUN으로 보고한다. Chromium 터치 에뮬레이션을 실제 기기 검사라고 부르지 않는다.

### 21.4 production E2E

실제 빌드의 기존 저장소 base 경로에서 새 원정을 시작한다. UI 명령으로 다음을 완주한다.

**실습 → 첫 룬 → 초원 보스 → 항구 상점 → 항구 보스 → 협곡 일반전 네 번 → 골렘 세 단계 → 12전투 제공 구간 완료**

첫 자원 로드 후 네트워크를 차단해 전투·사전·로컬 저장이 계속 작동하는지 확인한다. 이것만으로 오프라인 재실행 PWA를 구현했다고 보고하지 않는다.
실제 전체 원정 시연과 지정 카드/저장을 주입한 합성 UI 검사는 구분한다.

### 21.5 성능

새 동사구와 관계절 조합이 제출을 수초씩 멈추게 하지 않도록 작업량·후보·깊이 한도를 검토한다. 16카드 대표 fixture의 분석 시간, 최대 후보, 한도 초과 여부를 전후 비교한다.
문제가 있으면 중복 파싱 캐시 등 필요한 국소 최적화를 적용한다. 정답 문장 목록으로 Parser를 대체하지 않는다.
입력 listener, ResizeObserver, 파티클과 animation의 정리를 검사한다. 시각 효과는 게임 RNG를 소비하지 않는다.

- Stage 3, 체력바, 부위 파괴, 도감, 형태 메뉴의 캡처. 가능하면 짧은 타격 영상도 제출하되 합성 상태인지 실제 플레이인지 표시한다.
- 최신 `PROGRESS`, `NEXT_STEPS`, `PROJECT_HANDOFF`, `ARCHITECTURE`, `LANGUAGE_SCOPE`, `KNOWN_ISSUES`.
- production build 성공과 기존 Pages base 경로 보존. node_modules, 로컬 캐시, 원본 영상 대량 파일, 비밀 설정은 commit하지 않는다.

원격 CI, PR 생성, 코드 완료, main 병합, 공개 배포는 각각 다른 상태다. PR만 만들었다면 공개 게임이 업데이트되었다고 말하지 않는다.
작업 종료 시 자신이 시작한 검증 서버와 브라우저만 정리한다. 사용자의 다른 작업을 종료하지 않는다.

최종 보고는 다음에 답해야 한다.

1. 새 프로필로 실제 12전투를 완료했는가?
2. 과거완료와 미래진행·완료가 실제 시간 열쇠로 작동하는가?
3. 골렘의 한 부위를 넘어 피해가 전달되지 않고 세 단계가 한 번씩 정산되는가?
4. 새 버프와 운석으로 일반 적 원킬이 가능하고, 구버전 저장은 원래 수치를 유지하는가?
5. 도감·순서 UI·technology 수정·기존 실습은 어떻게 검증했는가?
6. 미실행 검사, 조정한 초깃값, 사용자의 실기·교육 검토가 필요한 부분은 무엇인가?
