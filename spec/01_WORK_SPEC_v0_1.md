## 1. 작업 지시와 범위의 우선순위

### 1.1. 이번 작업에서 실제로 완성한다

- **새 Vanilla JavaScript + ES Modules + Vite 프로젝트**. 기존 단일 HTML을 분해·이식하는 작업이 아니다.
- 여행자 1명, 난이도 1, 어휘 선택 초급/기본/심화/자유.
- 30장 조건부 랜덤 시작 덱, 첫 손패 6장, 손패 10장, 턴당 드로우 3장, 전투당 교환 4회, 6턴.
- 클릭·터치·드래그 편집, 형태 선택, 손패 회수, 다중 교환, 준비 행동, 공격 제출.
- **등록된 현재형 기본 평서문을 실제 분석하는 로컬 결정론적 Grammar Engine**. 1·2·3형식, 기본 NP/AP/AdvP/PP와 최소 오류 진단.
- 다섯 핵심 엔진의 책임 분리와 `AnalysisResult → AttackResolution` 계약.
- 제출 뒤 한글 문법명·카드 점등·역할명·점수 연쇄·오른쪽 룬 반응·돌진·타격.
- 초기 룬 10종, 슬롯 3개, 중복 획득 Lv.1~3, 룬 재배열, 기존 룬 교체·취소.
- 단어 보상·연마·제거·룬·건너뛰기 재화의 실제 정산. 1스테이지 2라운드의 매 원정 룬 기회.
- Stage 1 세 전투, 이모지 적, 조작 튜토리얼, 첫 보스, 성공·패배·빠른 새 원정.
- 내 덱/드로우/버린 더미 보기, 원정 사전, 기본 문장 도감, 최근 공격 기록.
- **최소 로컬 개인기록 + 안전 지점 수동 저장 3슬롯**. 정상 플레이·문장 검사·저장에 Firebase를 요구하지 않는다.
- 개발 전용 문장 샌드박스와 자동 테스트, 배포된 것과 같은 빌드의 브라우저 검증.
- 모듈형 원본 ZIP, 빌드 완료된 정적 배포 ZIP, 사용자가 이해할 수 있는 한국어 실행·배포 안내.

### 1.2. 구조와 메타데이터만 남기고 이번 플레이에는 넣지 않는다

- Stage 2~10, 전투 48, 무한 모드, 난이도 2~5, 다른 캐릭터.
- 4·5형식 및 과거·진행·완료·수동·관계절·가주어·가정법 등 후속 판정 코드.
- 전체 28종 룬의 실효과, 복잡한 희귀 룬 업적. 이번에는 초기 10종만 활성화한다.
- 전체 상점 UI·실제 구매. **상점은 2스테이지 입장부터이므로 Stage 1 버전에 억지로 끼워 넣지 않는다.** 위치·상품·횟수 계약은 보존한다.
- 황금·공명 카드 특수효과: 타입·데이터 자리만 유지하고 0.1의 획득·강화 UI에는 노출하지 않는다. 연마 +1~+3만 먼저 구현한다.
- Firebase 계정·동기화·Top 100 실제 랭킹, Cloud Functions, 서버 검증.
- PWA 설치·Service Worker 기반 오프라인 재실행·네이티브 앱 포장.
- 완성형 이미지·음악 제작. Asset ID와 이모지/CSS/합성 효과음으로 시작한다.

**다음 확장할 자리와 가짜 구현은 다르다.** 미구현 기능은 구현되지 않았다고 표시하며, 활성 버튼·가짜 순위·작동하지 않는 룬으로 출시하지 않는다.

### 1.3. 원본 사용·계정 변경 금지

- 실수로 첨부된 **DSbattleroyal HTML 및 그 코드를 열어 분석·복사·참고·변형·이식하지 않는다.** 어떤 파일도 기반으로 삼지 않는다.
- 다른 DS 게임도 이번 프로젝트의 코드 베이스가 아니다. 폴더에 함께 있더라도 제외한다.
- 허용 자료는 이 인계 묶음, 센텐스 발라트로 관련 기획 문서, 필요한 공식 기술 문서다.
- 기존 GitHub 저장소의 코드나 실제 배포를 덮어쓰지 않는다. 새 작업 폴더와 브랜치에서 만들고, 실제 Push/게시/서비스 연결은 별도 사용자 요청이 있을 때만 한다.
- 사용자의 Firebase 설정이나 기존 프로젝트 키를 찾아 연결하지 않는다. 0.1은 서버 설정 없이 실행해야 한다.
- ChatGPT의 대화 브랜치와 Git 브랜치는 별개다. Work 런타임에 이전 대화의 파일·설치 환경이 자동 존재한다고 가정하지 않는다. 인계 자료를 먼저 확인한다.

### 1.4. 합의·초기값·이번 보완의 구분

- **합의:** 장르, 학습 철학, 전투 자원, UI 방향, 룬 방식, 총 스토리 구조, 최신 상점 6회, 보상 확률 등.
- **초기 테스트값:** 카드 10점·연마 단계당 +5·무오류 +20·HP 70/120/220·문장 16장·룬 배수와 일부 보상 가중치. 이 값으로 구현하되 테스트 결과를 근거로 변경할 수 있다.
- **이번 구현 보완:** 첫 초회 1-1의 카드 보상 고정, 정확한 0.1 종료 상태, 최소 저장, 손패 가득 찼을 때 교환 동작, 미연결 카드 점수 배제, 오류 상태 구분, 배포 포장 방식 등. §24에서 이유를 밝힌다.
- 완성을 위해 숫자를 바꿔야 한다면 이전값/이유/새값/영향/재검증을 `DECISIONS.md`에 남긴다. 합의한 게임 철학이나 범위를 몰래 변경하지 않는다.

## 2. 절대 보존할 게임·교육 원칙

### 2.1. 영어 문제를 맞히면 공격하는 게임이 아니다

**단어 카드 자체를 조립한 영어 문장이 공격이다.** 정답 문장 하나를 암기해 배열하는 게임, 객관식 퀴즈, 자유 입력 작문 평가 서비스, 범용 영어 파서를 만들지 않는다.

선별한 단어·허용 형태·대표 Frame을 이용해 ‘작고 잘 설계된 영어 세계’를 만든다. 학생은 동일한 문형을 매번 다른 어휘로 구성한다. 기본 어휘를 골랐다고 점수나 희귀도에서 불리하게 만들지 않는다.

### 2.2. 안내하되 강제하지 않는다

지역 중점 문법은 이득을 주지만 가능한 다른 빌드도 존중한다. Stage 1에서는 1형식만으로도 공략 가능한 경로를 마련한다. 평범한 선택으로 첫 지역이 가능해야 하며 강력한 룬을 반드시 뽑게 만들지 않는다. 고점 빌드가 보스를 한 번에 잡는 결과도 막지 않는다.

### 2.3. 문법 검사는 제출 뒤에만

문장을 배열하는 동안 Grammar/Scoring을 호출해 정오·역할·콤보·예상피해·보스 조건 충족을 노출하지 않는다. 기존 제출의 결과로 현재 문장 점수를 추정 표시하지도 않는다.

편집 중에는 카드 품사·선택된 형태·위치·한도·터치 피드백만 제공한다. 튜토리얼의 다음 안내도 카드 이동이나 제출 등 **조작 사건**으로 진행한다. 공격 확정 뒤에만 문법이 드러나고 숫자가 상승한다.

### 2.4. 단순한 설명, 정확한 인정

전투: ‘완전한 문장!’, ‘주절 · 3형식!’, ‘부사 수식!’, ‘주어-동사 일치 -10’ 등만 짧게 표시한다. 필요한 역할명은 S/V/O를 한글 이름과 함께 빠르게 켰다가 끈다.

도감: 해당 구조를 처음/최고로 사용한 **플레이어 자신의 문장**, 사용 횟수·최고위력, 필요시 중학교 핵심규칙 한 줄. 모든 뜻 차이나 언어학 이론을 설명하지 않는다.

### 2.5. 복수 분석을 점수 중복으로 쓰지 않는다

전체 카드열을 설명하는 정상 분석이 있으면 학생의 의도와 무관하게 인정한다. 동등한 해석은 학교 문법용 대표 결과로 정규화한다. 같은 구조의 별칭/경쟁 후보는 점수 한 번, 실제 서로 다른 카드·절의 의도된 시너지는 각 규칙에 따라 계산한다.

**‘너그러운 인정’은 ‘근거 없이 맞다고 표시’가 아니다.** 미구현된 구조를 검증하지 못했다면 ‘이번 버전에서 판정할 수 없음’으로 돌려보낸다. 게임 오류를 문법 오류라고 표시하지 않는다.

## 3. 기술 구성과 프로젝트 골격

### 3.1. 작은 모듈형 웹앱

- Vanilla JavaScript ES Modules + Vite. 공개 API에는 JSDoc 타입과 입력 검증을 작성한다.
- UI는 HTML/CSS, 효과는 CSS/Web Animations와 필요할 때 Canvas 2D. React·Next·Redux·서버 프레임워크·ECS·범용 플러그인 DSL은 도입하지 않는다.
- 데이터는 JSON 또는 순수 데이터 모듈. 함수·DOM을 JSON 데이터에 저장하지 않는다.
- 테스트는 Node 내장 테스트 또는 하나의 경량 테스트 러너 중 하나를 선택한다. 브라우저 E2E는 Playwright를 개발 의존성으로 사용할 수 있다. 사용자에게 테스트 환경 구축을 떠넘기지 않는다.
- 의존성은 필요한 것만 설치하고 `package-lock.json`에 고정한다. 실제 사용한 Node/Vite/브라우저 버전을 보고서에 남긴다.
- Runtime은 외부 CDN·폰트 다운로드·AI API·원격 DB에 의존하지 않는다. 초기 핵심 데이터와 필수 효과를 로컬 정적 번들에 담는다.

폴더 수를 맞추기 위해 빈 파일을 양산하지 않는다. 작은 관련 구현은 합쳐도 되지만 다섯 엔진과 상태 변경 책임은 분리한다. 보스 이미지가 없어도 정상 보이는 fallback을 두고 실제 없는 이미지 URL을 무한 요청하지 않는다.

### 3.3. Public API와 방향

| 모듈 | 입력 → 출력 | 하지 않는 일 |
|---|---|---|
| Grammar | SentenceSnapshot + LanguageRegistry/Capability → AnalysisResult | 점수·룬·보스·어휘 난도 보정·DOM·서버 |
| Scoring | Analysis + 사용 카드 스냅샷 + Balance → ScoreResult | 영어 재분석·룬 선택·상태 수정 |
| Rune | Analysis + ScoreResult + 룬/카드 읽기 스냅샷 → RuneResult | 영어 재분석·HP 변경 |
| Stage/Boss | Analysis + postRuneScore + 지역/적 스냅샷 → EncounterResult | Parser 규칙 변경·실제 state mutation |
| Presentation | AttackResolution + viewContext → 완료/중단 결과 | 점수·피해·드로우·보상 재계산 |
| RunController | 사용자의 Command → 검증·엔진 호출·원자적 상태 반영 | 다른 엔진의 내부 함수를 우회 호출 |

**상태 변경은 RunController 한곳**, 계산 엔진은 읽기 전용 입력과 결과만 사용한다. 작은 통합 함수로 공격 파이프라인을 조율하고 글로벌 이벤트버스로 암묵적 연쇄를 만들지 않는다.

운영 룬은 공격 시가 아니라 `deriveCombatRules(base, character, difficulty, equippedRunes)`에서 계산한다. 동일 Rune 모듈의 별도 API로 처리하며 새로운 엔진을 만들지 않는다.

## 4. 전투 자원과 경계 규칙

| 항목 | 0.1 기본값 |
|---|---:|
| 시작 덱 | 30장 |
| 시작 손패 | 6장 |
| 손패 한도 | 10장 |
| 문장 조합대 | 16장, 초기 테스트값 |
| 2턴 이후 시작 드로우 | 3장 |
| 교환 행동 | 전투당 4회 |
| 교환 한 번의 장수 | 현재 손패에서 원하는 수, 1장 이상 |
| 행동 턴 | 전투당 6턴 |

첫 턴은 시작 손패 6장만 지급한다. 여기에 턴 드로우 3장을 또 더하지 않는다. 정상 공격 또는 준비 행동만 턴을 1 소모하고, 카드 편집·형태 변경·사전 보기·교환은 턴을 소모하지 않는다.

### 4.1. 네 영역과 실제 카드 보존

`deck.activeCardIds`는 이번 원정의 현재 보유 덱이다. 전투에서는 모든 활성 카드가 DRAW/HAND/SENTENCE/DISCARD 중 정확히 한 곳에 존재한다. Sentence는 `{cardInstanceId, selection}` 배열이며 손패 한도에서 제외한다. `formId`를 CardInstance의 영구 값으로 저장하지 않는다.

- Draw의 0번: 다음에 뽑힐 카드. UI는 이 순서를 보여 주지 않는다.
- Hand/Sentence: 좌→우 순서.
- Discard의 0번: 가장 최근 버린 카드.
- 사용·교환한 카드 모두 Discard로 간다. 별도의 다섯 번째 ‘사용 더미’는 두지 않는다.
- 다음 전투에는 현재 activeCardIds 전체를 새로 셔플한다. 강화·룬·재화·제거 결과는 유지한다.

### 4.2. 드로우·손패 가득 참

실제 드로우 수는 `min(요청 수, 빈 손패 공간, 순환을 통해 얻을 수 있는 카드 수)`다. 손패 9장에서 3장 요청이면 1장만 받는다. 못 받은 2장은 저장해 두었다가 다시 주지 않는다. 손패 10/10을 알려 주며 카드가 몰래 삭제되지 않는다.

Draw가 부족하면 남은 카드부터 뽑고 Discard만 셔플해 부족분을 이어 뽑는다. 두 더미가 모두 비면 가능한 만큼만 받고 정상 종료한다. Hand/Sentence는 절대 재셔플에 포함하지 않는다.

교환은 선택한 N장을 먼저 Discard로 옮기고 교환 횟수 1 차감 후 N장 요청을 한 번 수행한다. 이 과정에서 Draw가 소진되면 방금 버린 카드도 다시 나올 수 있다. 0장 선택·없는 ID·중복 ID·남은 횟수 0이면 상태를 바꾸지 않는다.

### 4.3. 편집과 조작 충돌 해소

- 손패 클릭: 현재 문장 오른쪽 끝에 추가한다.
- 손패 드래그: 표시된 삽입 위치에 추가한다.
- 문장 카드 클릭: 손패 끝으로 회수하고 그 카드의 현재 형태 선택은 초기화한다.
- 문장 내부 드래그: 순서를 재배열한다. 형태는 유지한다.
- **형태 버튼은 카드 본체 클릭과 분리**하고 이벤트 전파를 막는다. 형태 메뉴를 열었다고 카드가 손패로 돌아가면 안 된다.
- 손패가 가득 차 회수가 불가능하면 짧게 알려 준다. 카드 한 장을 먼저 조합대로 이동할 수 있다. 양쪽 모두 한도에 찬 경우에는 **손패 카드와 문장 카드의 직접 맞교환**을 지원한다. 카드 몸통에 놓으면 ‘교체’, 카드 사이에 놓으면 ‘삽입’ 표시를 달리한다. 실패한 드래그는 원위치.
- 교환 모드에서는 손패 클릭이 ‘문장 추가’가 아니라 ‘교환 선택 토글’이다. 모드·선택 N장·잔여 횟수를 명확히 표시한다. 취소는 무손실.
- Undo는 최근 편집(이동·형태·순서)만 되돌린다. 교환/드로우/공격/보상/RNG까지 되돌리는 Undo를 만들지 않는다.

### 4.4. 턴 종료와 마지막 공격

1. 정상 공격의 최종 결과를 계산한다.
2. 카드 이동·HP·턴 -1 등을 한 번 커밋한다.
3. **적 HP가 0이면 승리 우선**. 마지막 6번째 공격이라도 패배 처리하지 않는다.
4. 적 생존 + 턴 0이면 패배, 다음 턴 드로우 없음.
5. 적 생존 + 턴 잔여면 연출 이후 다음 턴 시작 드로우를 한 번 지급한다.

준비는 문장/손패를 유지한 채 턴을 소모한다. 마지막 턴 준비에는 ‘이대로 넘기면 패배합니다’ 확인을 둔다. 실시간 시계나 적의 자동 공격으로 턴을 줄이지 않는다. 플레이어 HP 시스템은 추가하지 않는다.

## 5. 여행자 시작 덱 생성

### 5.1. 품사와 물리적 장수

명사 6 + 대명사 5 + 동사 8 + 형용사 4 + 부사 2 + 관사/한정사 3 + 전치사 2 = **30장**.

- 대명사: I/you/he/she/they 각각 한 장. it/we는 일반 카드 풀에는 존재할 수 있다.
- 관사: a/an 카드 2장 + the 1장. a와 an은 서로 다른 카드가 아니다.
- 동사: be 2장 + SV 가능한 동사 2장 + SVO 가능한 동사 3장 + 다중 Frame이면서 현재 지원 기본 Frame이 있는 동사 1장.
- 전치사: in/on/at/with 중 다른 후보 두 장. 초기부터 to/that을 기본 덱에 강제로 넣지 않는다.
- 명사 최소 4종, 형용사 최소 3종, 비고정 단어의 시작 사본은 기본 최대 2장. 전체 고유 Lexeme는 기본 최소 20종을 목표로 한다.
- 부사: 정도 수식용 한 장(very 또는 really), 동사/절 수식용 한 장. 단어와 실제 용법을 검증한다.

한 동사가 여러 Frame을 가지더라도 **슬롯을 두 번 채운 것으로 계산하지 않는다.** 예를 들어 read 한 장이 SV와 SVO 역할에 모두 가능해도 물리적 카드 슬롯은 하나다. Coverage와 실제 장수는 따로 검사한다.

### 5.2. 어휘 수준별 생성

공통 문법 재료는 모든 모드에 동일하다. 콘텐츠 슬롯의 문법 역할·게임 등급을 먼저 정하고, 그 안에서 어휘 모드로 단어를 고른다. 심화 모드에서 자동사 슬롯을 없애고 추상 타동사만 넣지 않는다.

0.1의 새 샘플 가중치: 초급=B100%, 기본=B40/S60%, 심화=B20/S30/A50%, 자유=B/S/A 동일 가중치. 해당 역할·Band 후보가 없으면 같은 역할의 공통/하위 Band로 fallback하고 trace에 남긴다. **이 가중치는 공식 교육 난도 분류나 검증된 최적값이 아니라 구현 시작점**이다.

카드 기본점수·보상 희귀도·적 HP·룬·정확성 정책은 어휘 수준별로 바뀌지 않는다. 난도명만 바뀌고 덱은 항상 동일한 가짜 설정도 금지한다.

### 5.3. 가능한 문장과 초기 패

생성 순서: 슬롯 계획 → 어휘 후보 선택 → 카드 사본 생성 → 기본 구조 Coverage 검사 → 부족한 슬롯만 제한적으로 교체 → 덱 확정 → 초기 패 준비.

시작 덱은 1·2·3형식 각각의 깨끗한 문장 경로가 있어야 한다. 명사구의 단수 관사, 목적어 카드, 선택 가능한 실제 형태까지 포함한다. 동사 태그 수만 세고 ‘문장 가능’이라고 판단하지 않는다.

**각 전투 최초 패에는 1~3형식 중 최소 하나의 실제 조합 경로를 보장**한다. 학생에게 답을 표시하지 않는다. 권장 구현은 검증된 짧은 구조 한 개의 카드 subset을 실제 덱에서 선택하고, 남은 패를 시드로 채운 뒤 손패 내 순서도 섞는 것이다. 새 카드를 생성하거나 무한 리롤하지 않는다. 원래 덱·패의 난수 추첨과 보정 정책을 분리해 기록한다.

3회 보장 패가 늘 똑같은 I/run이 되지 않도록 frame/lexeme 후보를 균형화한다. 튜토리얼은 실제 생성된 패에 맞게 대상을 찾되 정답 배열을 미리 강제하지 않는다.

생성 재시도는 최대 32회 등 유한 한도를 둔다. 실패하면 같은 모드의 검증된 fallback 덱으로 전환하고 개발 trace를 남긴다. 정상 seed의 fallback 과다 사용은 데이터 결함이며 숨기지 않는다.

### 5.4. 준비 기회와 승리의 구분

초기 패가 가능하다는 사실은 전투 승리를 보장하지 않는다. 적 HP는 실제 6턴/교환/패 보존 시퀀스로 시험해야 한다. 매 턴 모범 정답을 다시 지급하거나 학생이 사용한 카드를 몰래 복제해 승리를 만들지 않는다.

## 6. WORD DATABASE: 실제 제작할 0.1 Seed

`04_LANGUAGE_SEED_MANIFEST_v0_1.json`에는 기존 후보에서 고른 **116 Lexeme 작업 후보**를 넣었다. 이것은 완성된 사전 JSON이 아니다. Work는 각 항목의 한국어 뜻·형태·Sense·FrameBinding·태그·지원 Capability와 테스트를 실제로 작성해야 한다.

후보는 공식 코퍼스 순위나 CEFR 인증 목록으로 주장하지 않는다. 기존 대화의 선정 어휘 중 첫 버전의 역할을 충족하도록 좁힌 후보이고, 잘못되거나 불필요한 Sense를 발견하면 제외 사유와 영향 검증을 남긴다. 최종 수는 80~120을 대략 목표로 하며 숫자 채우기를 위해 불안정한 단어를 넣지 않는다.

### 6.1. 언어 데이터와 게임 데이터

```text
Lexeme: id, lemma, pos, morphologyId, senseIds, vocabBand
Morphology: formId, surface, grammaticalFeatures, allowedRoleCandidates
Sense: id, glossKo, frameBindings, countability/referent/semanticTags 등
Frame: required slots + optional complements + supported adjuncts
CardDefinition: id, lexemeId, baseScore, rarity, displayCategory, availability
CardInstance: instanceId, cardDefId, polishLevel, specialEffectId(null in v0.1)
```

- `starterEligible/rewardWeight/rarity`는 언어 DB가 아니라 CardDefinition/PoolPolicy에 둔다.
- Sense/FrameBinding의 `requiredCapabilityIds`를 사용한다. 언어 DB에 `stage=8`이나 게임 점수를 넣지 않는다.
- 형용사·부사의 어려운 정도를 카드 공격력으로 바꾸지 않는다.
- 동사 사용 가능성을 무조건 Lexeme 전체에 걸친 boolean으로 처리하지 않는다.
- 관사 없는 school/home 사용을 허용하려면 문맥 한정 규칙을 등록한다. `bareUsageAllowed=true` 하나로 ‘I read school’ 같은 모든 단수 NP를 자동 허용하지 않는다.
- `home`의 장소부사 사용 등 인정할 제한 역할은 명시적인 role로 등록한다. 카드 앞면 분류는 고정하고 정상 사용 범위를 사전에 짧게 알려 준다.
- 명사 Sense의 count/mass, person/animal/thing 태그는 최소한만 정의한다. 의미가 우스운 문장을 현실성 때문에 막지 않는다.

### 6.2. 형태 선택

0.1 플레이 메뉴는 현재형 기본/3인칭단수, be의 am/is/are, 명사 단복수, a/an, 대명사 주격/목적격/소유한정형까지 제공한다. 비교급·과거·분사 등은 스키마에 담아도 현재 미지원 메뉴에 노출하지 않는다.

`be`는 인칭·수별 현재형을 명시하고, `read`처럼 같은 철자의 후보를 지원할 수 있게 surface와 grammatical form을 분리한다. **같은 표면어가 여러 문법 역할을 가질 때 숨은 클릭 메뉴의 formId만 보고 정상 문장을 오답 처리하지 않는다.** formId는 허용된 후보 집합과 표시의 근거이며 Grammar가 해당 카드/표면형의 가능한 역할을 검증한다. 다른 Lexeme의 자유로운 품사 변경까지 허용하는 것은 아니다.

형태 변경은 한 장의 상태 변경이다. `has been reading`, `a book`, `more beautiful`을 한 장의 형태로 생성하지 않는다. 한 장=한 실제 단어, 문장부호와 자동 첫 글자 대문자화만 카드 비용이 없다.

### 6.3. 보상 카드 등급과 활성 범위

일반/고급/희귀 CardDefinition을 분리한다. 최소 각 보상 등급에 실제로 사용 가능한 후보가 있어야 한다.

0.1에서는 희귀 연결 카드 `to`, `that`에 **전치사 to+NP / 지시한정사·대명사 that**의 현재 가능한 역할만 구현할 수 있다. 이는 이전 기능어 계약의 부분 집합이다. to부정사·관계절은 0.1에서 판정하지 않으며 사전에 가능한 역할만 노출한다. `I go to school.`, `I like that book.` 같은 실제 문장을 테스트한다.

고급 후보는 make/give/show/help/see 등 등록된 기본 용법으로도 쓸 수 있는 카드에서 골라 첫 시작점을 만든다. 등급은 기존 게임적 생산성 구분의 초기값이며 정확한 후보표는 명시한다. 미래 문법만 가능한 빈 카드를 보상으로 주지 않는다.

한 희귀 묶음에 적법한 서로 다른 후보가 두 개뿐이라면 두 개만 보여 준다. 세 개를 채우기 위해 가짜 중복이나 등급 변경을 하지 않는다. 이것은 카드 보상 ‘최대 세 후보’ 규칙에 부합한다.

## 7. Grammar Engine의 0.1 지원 범위

### 7.1. 반드시 작동할 구조

- 현재형 긍정 평서문, 한 개의 주절.
- SV, SVC_ADJ, SVC_NP, SVO.
- 주어/목적어/보어로 사용하는 명사구와 대명사.
- a/an/the/소유한정사/this/that + 명사, bare plural, bare mass.
- 명사 앞 형용사, 부사+형용사, 반복 very/really 강조.
- 허용된 동사/절 부사 위치. 단어별로 대표 위치와 허용 범위를 둔다.
- in/on/at/with와 보상 to의 기본 PP. 동사 부사어와 간단한 명사 후치수식.
- 주어-동사 일치, 기본 명사구의 수·관사·대명사 격 검사.
- 등록된 be+위치 구문. 내부 frame.beLocative를 학교표시 1형식으로 매핑하되, 장소 의미에 필요한 PP/부사가 실제 있는 경우만 허용한다.

### 7.2. 0.1에서 인정 완료인 것처럼 표시하지 않을 구조

복문/관계절/등위절/의문문/명령문/부정문/to부정사/동명사/진행/완료/과거/수동/4·5형식/비교 등은 이후 Pack 대상이다. 관련 형태나 카드가 샌드박스 fixture로 들어오면 **UNSUPPORTED**로 안전 반환한다.

`She made ...`를 Stage 1 현재형 테스트의 정상 사례에 섞지 않는다. 문장 목록에서 불규칙 철자를 자동 치환하고 현재형으로 채점하는 것도 금지한다.

### 7.3. 판정 방식

권장 방식은 Lexeme 후보 → NP/AP/PP 구성 → 기본 Clause Frame 매칭 → 일치/정확성 검사 → 전체 카드 사용 범위 검증 → 대표 분석 정규화다. 단어 문자열 부분일치/정규식 한 줄/정답문장 배열만으로 문장 전체를 판정하지 않는다. 패턴 매칭은 형태·데이터 lookup의 보조 수단이다.

전체 문장을 설명하는 정상 후보를 우선한다. 부분 분석이 점수가 높다는 이유로 선택하지 않는다. 단어열 앞부분 ‘She likes dogs’만 인정하고 뒤의 불명확한 단어를 전부 유효 카드점수로 넣지 않는다.

탐색은 카드 수 16, 후보 수/노드 수 상한, 재귀 깊이·작업량 예산을 둔다. 문장 전체 permutation이나 무제한 복구 탐색은 금지한다. 제한에 걸리면 ENGINE_LIMIT/UNSUPPORTED로 무손실 반환한다.

### 7.4. 네트워크와 실행 성능

Parser/Scoring에 fetch·LLM 호출이 없다. UI와 독립된 순수 함수로 테스트 가능해야 한다. 느려지는 경우 한 개의 전용 Web Worker로 옮길 수 있게 하되 측정 없이 많은 Worker/서비스를 만들지 않는다. 단순 Promise만 씌우면 CPU 작업이 메인 스레드에서 분리된다고 생각하지 않는다.[T6]

대표 2~16카드 테스트의 계산 p95 100ms 이내를 초기 목표로 측정한다. 이는 보장된 실측값이 아니며 Work가 환경과 결과를 보고한다. 넘으면 진행 표시와 유한 취소/실패 경로를 제공한다. 애니메이션 시간을 파서 계산시간으로 오인해 보고하지 않는다.

## 8. 판정 상태·오류·최소 피드백

| 상태 | 의미 | 공격/자원 |
|---|---|---|
| VALID | 전체 지원 구조가 정상 | 공격, 카드 사용, 턴 -1 |
| VALID_WITH_ISSUES | 구조는 확인되나 명시된 정확성 오류 | 부분감점 후 공격, 카드·턴 사용 |
| INVALID_CORE | 지원 기본 범위에서 필수 구조 실패 | 공격 없음, 카드·턴·교환/RNG 보존 |
| UNSUPPORTED | 미지원 구조/불확실한 범위 | 오답 단정 없음, 자원 보존 |
| ENGINE_ERROR | 내부 예외/잘못된 데이터/실행 오류 | 기술오류 안내·로그, 자원 보존 |

`ENGINE_ERROR`를 UNSUPPORTED로 숨겨 Parser 결함을 언어 범위 탓으로 돌리지 않는다. 모호함은 분석 결과의 candidates/ambiguities에 기록하고, 정상 대표 분석이 있으면 VALID이다. 단순히 후보 두 개라는 이유로 매번 학생을 되돌리지 않는다.

### 8.1. 허용할 부분 복구

- She like dogs. → SVO를 확인하되 일치 오류.
- I have book. → SVO를 확인하되 한정사 필요.
- She likes a dogs. → 하나의 관사·수 불일치 오류. 같은 원인으로 관사/수/한정사 오류 3회 중복 차감 금지.
- I like she. → SVO를 확인하되 목적격 오류.
- I very like dogs. → very의 명백한 잘못된 수식 역할을 진단하고 기본 SVO는 보존할 수 있다. **그 very의 카드점수·수식점수·부사룬 효과는 인정하지 않는다.** 한 원인으로 카드점수 배제와 고정감점을 중복 부과하지 않는다.

### 8.2. 허용하지 않을 복구

She happy.에 is를 자동 생성하거나, She dogs likes.의 어순을 몰래 바꾸거나, 부족한 목적어를 채워 VALID로 만들지 않는다. 학생이 쓰지 않은 카드가 점수·콤보의 근거가 되어서는 안 된다.

### 8.3. 메시지

- VALID: 제출 전 결과 없음, 제출 뒤 ‘완전한 문장!’.
- WITH_ISSUES: ‘주어-동사 일치 -10’처럼 원인과 관련 카드 두 곳을 잠깐 강조. **‘완전한 문장!’ 및 무오류 보너스는 없음**. 필요하면 ‘문장 구조 확인’이라는 중립 문구.
- INVALID: ‘동사가 필요합니다’, ‘문장 순서를 확인하세요’ 등 하나의 대표 원인과 수정할 구간.
- UNSUPPORTED: ‘이 구조는 0.1에서 아직 판정하지 않습니다.’
- ENGINE_ERROR: ‘판정 처리에 문제가 생겼습니다. 카드와 턴은 그대로입니다.’ + 개발용 errorId.

문장 교정 정답을 자동 완성하거나 긴 설명 팝업을 띄우지 않는다. 미지원 문장에 대한 “완전한 문장 +20”을 추측으로 지급하지 않는다.

## 9. 점수 공식과 이벤트 계약

### 9.1. 초기 점수값

| 항목 | 값 |
|---|---:|
| 사용 카드 기본점수 | 각 10 |
| 연마 단계당 추가 기본점수 | +5, 최대 +3 |
| 전체 무오류 문장 | +20 |
| 1형식 | ×1 |
| 2형식 | ×1.2 = 6/5 |
| 3형식 | ×1.5 = 3/2 |
| 명사를 수식하는 형용사 | 해당 형용사 카드당 +5 |
| 정상 부사 수식 | 해당 부사 카드당 +5 |
| 정상 전치사구 | PP당 +10 |
| 지역 보너스 | 1·2·3형식 중 하나가 인정되면 공격당 ×1.25, 한 번 |

주격보어 happy 자체는 형용사 **수식** +5를 받지 않는다. ‘She is happy.’의 점수는 기존 60을 유지한다. `very happy`에서는 very의 부사 수식 +5만 붙는다.

### 9.2. 계산 순서

1. 실제 제출 카드 기본점수 합산(연마 포함).
2. 오류가 있는 원인별 정확성 감점 및 근거 없는 카드 기여 배제. 합계는 0 아래로 내려가지 않게 한 번 clamp.
3. 전체 무오류일 때만 +20.
4. 주절 문형 배수 한 번.
5. 현재 구현된 추가 문법 콤보. 0.1에는 고급 콤보 없음.
6. 형용사 수식/부사/PP 보너스. 같은 구조의 중의적 후보 중복 금지.
7. 특수 카드 효과 자리. 0.1은 비활성; 연마를 다시 더하지 않는다.
8. 오른쪽 룬 슬롯 위→아래 순서.
9. 지역 보너스 한 번.
10. 보스 규칙. Stage 1은 추가 장막·면역 없음.
11. 최종 공격위력/실제 HP 감소/오버킬.

배율은 `{num, den}`으로 보존하고 **각 곱셈 후 내림**한다. 0.1은 안전한 범위의 정수 연산을 한 유틸리티로 모으고 Infinity/NaN/unsafe integer를 검사한다. 무한 모드용 BigInt 전체 구현은 후속이다. 숫자 표시 애니메이션 중간값은 게임 값이 아니다.

### 9.3. 감점

일치 -10, 대명사 격 -10, 기본 관사·한정사·명사구 수 관련 단일 원인 -5를 초기값으로 사용한다. 실제 사용 불가 카드(예: 동사 앞에 직접 붙인 very)의 경우 그 카드 기본점수 기여만 한 번 제외하며, 해당 카드의 수식·룬 히트도 제외한다. 같은 원인에 추가 고정감점을 또 붙이지 않는다.

부분 오류가 있어도 복구된 주절 Frame 히트는 문형·관련 룬·지역보너스의 근거가 될 수 있다. 무오류 문장/수정 룬은 발동하지 않는다. 이 정책을 `hit.validity=VALID|RECOVERED`와 명시적인 score/rune 조건으로 표현한다.

### 9.4. 정답 산술 기준(룬·연마 없음)

| 문장 | 지역 전 | Stage 1 지역 후 |
|---|---:|---:|
| I run. | (20+20)×1 = 40 | 50 |
| She is happy. | (30+20)×1.2 = 60 | 75 |
| I like dogs. | (30+20)×1.5 = 75 | 93 |
| She like dogs. | (30-10)×1.5 = 30 | 37 |
| I have book. | (30-5)×1.5 = 37 | 46 |
| She likes the big dog. | (50+20)×1.5+5 = 110 | 137 |
| She is very very very happy. | (60+20)×1.2+15 = 111 | 138 |
| I run in the park. | (50+20)×1+10 = 80 | 100 |

이 표는 **산술 기대값**이다. 실제 Grammar 파서의 결과와 결합해 end-to-end로 다시 검사해야 한다.

### 9.5. ScoreEvent

모든 점수 변화에 유일한 eventId, phase, sourceType/sourceId, operation, operand, before/after, evidenceRefs/cardIds, labelKo가 있다. UI가 숫자를 다시 계산하지 않는다. 같은 이벤트는 출처와 대상이 무엇인지 추적 가능해야 한다.

```json
{
  "eventId": "attack.12:score.6",
  "phase": "MAIN_FRAME",
  "sourceType": "GRAMMAR",
  "sourceId": "FRAME.SVO",
  "labelKo": "주절 · 3형식!",
  "operation": "MULTIPLY",
  "operand": {"num": 3, "den": 2},
  "before": 50,
  "after": 75,
  "evidenceRefs": ["hit.mainFrame"],
  "highlightCardIds": ["card.she", "card.like", "card.dog"]
}
```

0.1에서 쓰는 GrammarTag는 `FRAME.SV/SVC/SVO`, `MODIFIER.ADJECTIVE`, `MODIFIER.ADVERB`, `PHRASE.PP`를 정규화된 레지스트리로 모은다. UI 문자열이나 같은 의미의 다른 tag를 여기저기 중복 정의하지 않는다.

## 10. 실제 구현할 룬 10종

`03_RUNE_SEED_v0_1.json`의 active 10종은 기존 ID/효과/Lv.1~3 값을 유지하고 최신 보석 이름을 사용한다. 같은 파일의 futureReference 28종 목록은 **후속 계획 참조용**이다. 현재 active pool과 합치지 않는다.

| ID | 이름 | 등급 | 조건/효과 | Lv.1 / Lv.2 / Lv.3 |
|---|---|---|---|---|
| rune.short | 호박 룬 | 일반 | 실제 사용 카드 4장 이하 공격 | ×1.25 / ×1.5 / ×1.75 |
| rune.sv | 루비 룬 | 일반 | 주절 1형식 | ×1.4 / ×1.8 / ×2.2 |

| rune.svo | 에메랄드 룬 | 일반 | 주절 3형식 | ×1.4 / ×1.8 / ×2.2 |
| rune.perfectSentence | 수정 룬 | 일반 | 전체 무오류 문장 | +20 / +35 / +50 |

### 10.1. 장착·중복·레벨

- 0.1은 기본 3슬롯. 후속 3스테이지/6스테이지 클리어 시 4/5슬롯은 로드맵에만 기록.
- 같은 룬 재획득은 동일 인스턴스 레벨 +1. 같은 ID 여러 슬롯 금지.
- 이미 Lv.3이면 새 보상 추첨에서 제외한다.
- 슬롯 만석이면 교체 대상을 고른 뒤 확정. 취소는 기존 상태/보상 기회를 보존한다.
- 교체한 룬은 원정 장착에서 빠지고 판매 재화를 주지 않는다. 별도 보관함 없음.
- 공격용 룬 순서는 편집 상태나 전투 밖에서 바꿀 수 있다. 공격 확정 순간 스냅샷 고정.
- 운영 룬의 전투 규칙은 전투 입장 때 한 번 계산. 이동/툴팁/창 재개로 손패·횟수를 다시 지급하지 않는다. 전투 중에는 소유 룬 교체/획득 자체가 없다.

### 10.2. 첫 룬 정책

**모든 원정에서 1-2 승리 보상은 RUNE**이다.

- 아직 첫 룬 소개를 본 적 없는 프로필: 수정/호박/구리 고정. 보여 준 시점에 첫 소개 플래그를 기록하되 frozen offer는 저장 복원 때 변경하지 않는다.
- 이후: 활성·해금 기본 룬에서 서로 다른 두 후보, 활성·해금 전체 풀에서 한 후보. 0.1에서는 둘의 풀이 대부분 같아도 정책 코드는 분리한다.
- 초회 첫 룬이 1-1 무작위 보상에서 먼저 나오는 충돌을 피하기 위해 **초회 안내 원정의 1-1은 CARD_COMMON 고정**으로 한다. 이것은 이번 인계에서 명시한 튜토리얼 예외다. 이후 원정 1-1은 정상 확률이므로 룬이 먼저 나올 수도 있고, 1-2의 보장 기회는 여전히 남는다.
- 튜토리얼 UI를 건너뛴다고 고정 첫 보상 정책/RNG가 달라지지 않는다. 게임 정책과 도움말 표시를 분리한다.
- 첫 룬 선택도 건너뛰기 +2 가능. 강제 획득하지 않는다.

### 10.3. 룬 후보 확률

기존 제안 일반60/고급30/희귀10은 **룬 후보 안의 조건부 가중치**다. 0.1에는 활성 희귀 룬이 없으므로 비어 있지 않은 룬 등급만 재가중한다. 단어 카드 보상표의 희귀5%를 바꾸는 것이 아니다. 같은 offer 내 중복 ID를 피하고 후보 부족은 유효한 수만 표시한다.

### 10.4. 사전 해금과 첫 빌드

초기 10종은 사용 가능. 일부 미래 해금 이벤트(예: Stage1 clear의 전달/산호 룬)는 프로필 메타에 기록할 수 있으나, runtimeReady=false이면 보상 후보에 넣지 않는다. 3회 플레이로 혜성 해금을 기록해도 혜성 효과를 구현하지 않았으면 장착시키지 않는다. 도감에는 ‘후속 버전’으로 명확히 구분한다. 본 작업은 모든 업적 조건 평가 DSL을 만드는 작업이 아니다.

## 11. 보상·재화·연마·제거

### 11.1. 보상표 (전투당 묶음 하나)

| 유형 | 일반 적 | 지역 보스 |
|---|---:|---:|
| CARD_COMMON | 50% | 0% |
| CARD_UNCOMMON | 10% | 10% |
| CARD_RARE | 5% | 10% |
| CARD_ENHANCE | 15% | 25% |
| CARD_REMOVE | 10% | 5% |
| RUNE | 10% | 50% |

튜토리얼 예외를 제외하고 이 확률로 보상 유형을 한 번 추첨한다. ‘카드65%’를 별도로 다시 곱하거나, 후보 세 장 각각 이 표를 적용하지 않는다. 각 카드 offer는 선택한 동일 등급의 최대 세 후보이며 A=지역/B=범용/C=변칙을 그 범위 안에서 사용한다.

선택지는 생성 즉시 RunState에 고정한다. 보상창 열기·저장·로드·교체 취소·UI 애니메이션이 재추첨을 일으키면 안 된다. 준비 기회 보정도 실제 설정에 없는 몰래 리롤 방식으로 넣지 않는다.

### 11.2. 정산

일반 승리 +2, 지역 보스 승리 +6. 보상을 받아도 지급한다. 카드 보상을 넘기면 추가 +3, 그 외 보상 넘기기는 추가 +2.

1스테이지를 보상넘김 없이 클리어한 기본 재화는 **10**이다. 이전 상점 배치의 첫 상점 재화22를 0.1 기준에 잘못 사용하지 않는다.

0.1의 강화 보상은 보유 카드 하나의 연마 +1이다. MAX+3 카드는 비활성화한다. 보상이 어떤 카드인지 선택하지 않은 채 연마 완료 처리하지 않는다. 제거는 보유 카드 인스턴스 하나를 덱에서 실제 제거한다. 마지막 카드/필수 Frame 손실 경고는 제공하되 정해지지 않은 강제 복구를 하지 않는다.

모든 대상이 max이거나 합법적인 대상이 없으면 이유와 건너뛰기 재화를 보여 준다. 다른 보상으로 몰래 바꿔 확률을 왜곡하지 않는다.

### 11.3. 원자적 선택

`offerId + choiceId`를 검증하고 새로운 카드 ID/룬레벨/덱/재화를 하나의 트랜잭션식 상태 변경으로 반영한다. 이미 resolved이면 재실행하지 않는다. UI double-click으로 두 장 지급하거나 skip gold를 두 번 받지 않는다.

연마 취소·룬 교체 취소는 offer를 미해결 상태로 남기고 진행을 막지 않는다. 다음 전투 시작은 보상 선택 또는 건너뛰기 정산 뒤에만 가능하다.

### 11.4. 상점 경계

0.1에는 상점을 플레이 화면으로 만들지 않는다. 이후 첫 상점은 **Stage2 전환·보스 예고·입장카드 후, Battle4 셔플 전**이다. 데이터의 전투번호만 맞춰 두고 없는 Stage2를 클릭하면 빈 화면이 되는 버튼을 만들지 않는다.

상점 서비스는 연마/특수강화 1회와 제거 1회, 각기 별도 자원이며 후속에 구현한다. 정확한 6회 일정은 §23에 유지한다.

## 12. Stage 1 실제 흐름과 종료 정책

### 12.1. 시작

로비에서 플레이어 이름 → 원정 설정(여행자, 어휘4종, 난이도1, 선택 seed) → 원정생성 → ‘시작의 초원’ 전환/보스 예고 → 1라운드.

처음부터 방번호·호스트·학생 참가·실시간 서버 로비를 만들지 않는다. 이름은 로컬 프로필의 표시명이다.

### 12.2. 세 전투

| 위치 | 표시 이름(이모지 임시안) | HP | 목표 |
|---|---|---:|---|
| 1-1 | 풀잎 슬라임 🌱 | 70 | 카드 조립→제출→점수·공격 |
| 1-2 | 숲 달팽이 🐌 | 120 | 교환·준비·형태/편집 경험 |
| 1-3 | 초원 수호자 🌳 | 220 | 첫 룬을 이용한 지역 보스 |

적 이름/이모지는 임시 자산안이다. 기능/UI를 위해 외부 이미지 생성이 필요하지 않다. 보스 HP는 플레이어의 성능에 맞춰 몰래 늘어나지 않는다. 지역 효과는 1~3형식 ×1.25이고 보스도 별도 배수/면역 없이 이 기준을 따른다.

### 12.3. 첫 튜토리얼

말풍선/초점 테두리로 한 번에 한 조작을 안내한다. 첫클릭→동사 카드/형태 버튼→제출→결과→교환/준비→첫 룬 순서를 학습 흐름에 맞춰 분산한다. 반드시 특정 단어를 특정 위치로 이동해야 다음 단계로 가는 고정 스크립트는 금지한다.

가이드 중에도 사전·설정·나가기·건너뛰기를 사용할 수 있다. 카드형태 팝업과 가이드가 서로 클릭을 가로막지 않도록 테스트한다. 두 번째 원정부터 강제 팝업은 끄며 설정의 ‘조작 안내 다시 보기’만 제공한다.

### 12.4. 첫 지역 클리어

3번째 적 처치 → 재화·보스보상·도감/해금 정산 → 보상 해결 → **‘시작의 초원 클리어 · 0.1 제공 구간 완료’**.

- 내부 run.status=`CONTENT_COMPLETE`, contentBoundary=`STAGE1_END`.
- 전체 스토리 완료(`CLEARED`/storyClearCount)를 기록하지 않는다.
- 난이도2, 새 캐릭터, 다회차 절대면역 보스, 무한모드를 해금하지 않는다.
- 커리큘럼 `pack.svoo` 개방을 기록하고 화면에는 ‘4형식 해금 — 2스테이지는 다음 버전에서 제공’ 정도로 범위를 알려 준다. 4형식 사용 실적·첫 문장은 생성하지 않는다.
- 기록 보기/저장/새 원정/로비 버튼은 실제 동작한다. ‘계속’으로 비어 있는 Stage2에 진입하지 않는다.
- 이 상태의 저장은 원정 ID·덱·룬·수치를 보존한다. 향후 Stage2 추가 시 마이그레이션 후 이어갈 수 있도록 하되 미래 호환을 이미 검증했다고 주장하지 않는다.

### 12.5. 패배·재시도

0턴·적 생존이면 남은HP/최고공격/남은교환 등 확인 가능한 사실을 표시한다. 공격 마지막 연출을 본 뒤 결과창을 띄운다.

버튼: **새 원정**, **수동 저장 불러오기**, **로비**. 자동 저장한 마지막 전투를 복원하는 것처럼 꾸미지 않는다. 시드 재도전은 같은 설정/버전/해금기준에서 시작하는 새 runId로 구분하고 기존 보상·강화를 가져오지 않는다. 동일 저장 재클리어는 반복 플레이 업적에 중복 계산하지 않는다.

## 13. 메인 화면과 카드 UX

### 13.1. 레이아웃

```text
┌──────────────────────────────────────────────────────────────┐
│ Stage 1-2 / 시작의 초원     적 이름 · HP 바 · HP 수치          │
│                         [이모지 적 공간]                     │
├─────────┬───────────────────────────────────────┬────────────┤
│남은턴6칸│      [제출 뒤 한글 콤보/누적 점수]     │루비 룬     │
│교환4    │                                       │수정 룬     │
│재화     │           [문장 조합대]                │빈 슬롯     │
│사전/기록│                                       │            │
│저장/설정│ [공격 확정] [준비: 다음턴 +3]          │            │
├─────────┴───────────────────────────────────────┴────────────┤
│ [DRAW 카드더미]       [손패: 최대10]        [DISCARD 더미]    │
│ 나의 덱/드로우 n       [교환 모드 / 확정]    버린 카드 n      │
└──────────────────────────────────────────────────────────────┘
```

점수판은 **문장 바로 위에 고정된 공간**을 두고 제출 때 강조한다. 제출 시 점수판과 문장 위치를 실제 교환해 화면을 흔들지 않는다. 보스 공간은 상단 약 20~25%를 초기 기준으로 확보하되 최소 해상도에서 문장/손패를 희생하지 않는다.

### 13.2. 대상 기기

데스크톱 1366×768/1920×1080, 태블릿 가로 1024×768/1180×820을 기준으로 테스트한다. 16:9 전체 화면을 통째로 축소만 해서 태블릿 글씨가 읽기 어려워지는 방식은 피한다. CSS Grid/Flex로 좌우 패널·카드 폭·줄바꿈을 조절한다.

문장 카드 16장은 두세 줄로 재배치할 수 있다. 줄 바꿈으로 영어 어순이 바뀌거나 드래그 위치가 어긋나지 않는다. 손패는 단어와 클릭 영역이 식별되는 정도로만 겹친다. 모바일 세로는 가로 권장 안내를 보여 주며 이를 모바일 지원 완료라고 보고하지 않는다.

### 13.3. 카드 정보

큰 영단어, 작은 한글 품사/다기능 카드 ‘연결어’, 기본점수/연마 표시, 작은 희귀도 표시를 사용한다. 카드 앞면에는 한국어 뜻을 항상 쓰지 않는다.

품사별 색 띠·테두리와 텍스트 배지를 함께 사용한다. 명사 파랑, 동사 빨강, 형용사 노랑, 부사 주황 등 일관된 테마를 데이터로 정의한다. 색만으로 필수정보를 전달하지 않는다. 룬 이름/색과 단어색을 맞추는 신규 보너스 없음.

### 13.4. 입력 구현

마우스/터치는 Pointer Events 공통 처리와 pointer capture/cancel을 사용한다.[T3] 마우스 hover에만 의존하지 않는다. 기본 터치 목표 44CSS px를 디자인 목표로 하고 키보드 focus가 보이게 한다. 키보드도 카드 선택→Enter로 이동, 메뉴로 형태/이동, Escape로 취소가 가능하도록 한다. 실수 Enter로 공격하지 않게 공격 버튼에만 명확히 연결한다.

터치 드래그 임계거리(초기값 8px)를 넘긴 뒤 클릭을 억제한다. 스크롤과 충돌하지 않는 카드 영역만 touch-action을 조절한다. 두 손가락/두 포인터가 동시에 같은 카드를 조작해도 한 동작만 인정한다. 회전·resize·pointercancel은 원위치 복구 또는 확정된 단일 동작으로 종료한다.

### 13.5. 덱·사전·기록

- **나의 덱:** 현재 activeCardIds 전체, 강화·보유장수·현재 영역을 확인. 실제 드로우 순서는 표시하지 않는다.
- **Draw 더미:** 남은 카드 내용은 볼 수 있으나 next-draw 순서와 난수정보는 숨긴다. 제목에 ‘순서는 공개하지 않음’.
- **Discard:** 현재 버린 카드와 최근 맨 위 카드, 실제 장수.
- **원정 사전:** 이번 원정에서 소개/획득/공개 보상으로 만난 Lexeme, 한글 뜻·품사·허용 형태·게임효과. 카드 제거 후에도 방문 어휘는 유지. 보이지 않은 미래 보상 단어를 미리 유출하지 않는다.
- **문장 도감:** 1~3형식·기본 수식 관련 자기 문장 기록. 보상을 받았다는 이유만으로 문법 사용 실적을 만들지 않는다.
- **최근 공격:** 이미 확정된 분석·점수 내역 보기. 그 화면이 재화/실적/피해를 다시 적용하지 않는다.

모달의 닫기/뒤로/스크롤이 동작하고 전투 입력이 뒤에서 눌리지 않는다. 저장/보상 중에도 화면이 배경만 남는 상태를 만들지 않는다.

## 14. 점수 연쇄·룬·공격·사운드

### 14.1. 눈에 보이는 공격 파이프라인

문장 잠금 → 카드별 점수 → 오류/감점 → 무오류 문장 보너스 → 주절 형식/역할 점등 → 수식 구간 → 공격용 룬 → 지역 보너스 → 최종 공격력 → 응축 → 카드 조립체 돌진 → 충돌 → HP 바 감소/피격/처치.

- 큰 한글 효과는 한 번에 하나씩, 누적 숫자는 같은 위치에서 변한다.
- 글자가 파티클 뒤에 묻히지 않는다. 지나간 이벤트는 작은 2~3줄 기록 또는 최근 공격 내역에 남긴다.
- NP 내부 형용사/부사/PP와 실제 문장 역할에 맞춰 카드 ID 구간을 강조한다.
- Stage1에서는 관계절 엔진을 만들지 않지만 renderer의 `connect(fromCardId,toCardIds)` primitive는 실제 작동하도록 만든다. 미래 관계절 연출 합성 fixture는 샌드박스의 **‘연출 샘플 · 실제 판정 아님’**에서만 검증하며 학생 기록·보상에 반영하지 않는다.

### 14.2. 점수 강도

점수 숫자는 점차 굵어짐·짧은 scale pulse·글로우·네온·상한 있는 작은 열기 효과로 반응한다. 정확한 숫자를 읽을 수 있게 하고, 수치가 커졌다는 이유로 UI가 영역 밖으로 밀리지 않는다. 자리수별 표기/축약 표시도 원본 정확한 수치를 툴팁/상세에 남긴다.

강도는 최종 피해/해당 전투의 고정 기준 위력으로 결정한다. 문법의 어려움·단어 Band가 직접 화면 충격을 결정하지 않는다. 현재 남은 HP가1이라는 이유만으로 평범한 공격을 초월 공격처럼 만들지 않는다.

### 14.3. 타격

예시 타이밍은 테스트 시작값: 카드 반응 70~110ms, 문법/룬 강조 250~450ms, 충전 120~220ms, 돌진 160~260ms, hit stop 40~100ms. 일반 제출은 약 1.5~3초, 다중 카드/룬 연쇄도 불필요한 대기를 줄여 검증한다. 속도 선택 1×/1.5×/2×는 결과에 영향 없음.

실제 쓰레드/브라우저를 busy-wait로 멈추지 않는다. hit stop은 연출 타임라인만 잠깐 정지한다. 화면 흔들림은 전투 배경·적에 제한하고 손패·문장 글자는 가능하면 안정적으로 남긴다. 강한 오버킬은 회전/휭 날아감/잔상을 허용한다.

0 피해나 면역의 미래 fixture는 장막에 튕기는 연출로 분리한다. HP0인 적이 정상 생존 피격 루프로 돌아오지 않는다. 의미없는 클릭 연타로 데미지를 더 주지 않는다.

### 14.4. 게임 상태와 화면 상태

계산/커밋은 애니메이션 전에 완료하되 화면에는 `hpBefore → hpAfter`를 impact 시점에 반영한다. RunState의 HP가 이미 감소했다고 적이 채점 시작 전에 사라져서는 안 된다. 전투용 viewSnapshot은 표시 전용이며 두 번째 게임 진실이 아니다.

Presentation 실패/취소/속도 변경/탭복귀에도 실제 결과는 한 번만 적용한다. 순서가 끝나거나 fallback fast-forward하면 최종 UI상태로 수렴하고 다음 입력을 해제한다. 이미 커밋한 공격을 다시 분석하거나 보상 정산을 재실행하지 않는다.

### 14.5. 사운드

Web Audio로 자체 생성한 간단한 카드/점수/룬/충전/충돌 효과를 실제로 재생한다. 유저 클릭 뒤 AudioContext를 활성화하고 autoplay 제한 실패는 조용히 처리한다.[T5] 한 개의 context와 Master/SFX 채널을 재사용한다.

강한 점수 연쇄는 음높이/음색/무게를 단계적으로 바꾸되 음량 상한과 동시 소리 수 제한을 둔다. 음소거·SFX 볼륨·효과 감소 설정을 제공한다. BGM 파일이 없으면 억지로 원격 음원이나 라이선스 불명 음원을 넣지 않는다. BGM Asset ID와 AudioManager의 교체 API만 준비한다.

부족한 이미지·오디오 파일, 소리 재생 거부, reduce motion 설정은 게임 진행을 막는 오류가 아니다. 작은 CSS/Canvas 효과로도 실제 손맛을 검증한다.

## 15. 공용 데이터와 원자적 상태 전이

### 15.1. 공용 값의 형태

게임 상태/저장은 문자열·유한 정수·boolean·null·array·plain object로 표현한다. DOM/Audio/Promise/Timer/Date/함수 객체는 들어가지 않는다. 런타임 index Map은 registry 내부 캐시로 가능하나 저장 데이터와 분리한다.

```text
RunState
  version, revision, runId, status
  config: character, vocabularyMode, difficulty, seed, contentProfile
  progress: stageId, roundIndex, battleNumber, contentBoundary
  activeCardIds, cardInstances
  vocabulary: encounteredLexemeIds
  runes: orderedInstanceIds, instances, slotLimit
  economy: gold
  combat: rulesSnapshot, phase, turnsRemaining, exchangesRemaining,
          drawIds, handIds, sentenceSlots, discardIds, enemyState,
          battleStartedSnapshotRef, actionSequence, settled
  reward: frozenOffer | null
  rng: deck/reward/shop/encounter stream states and algorithm version
  eligibility: runStartUnlockBaseline + runOwnUnlocks
  stats: counters, lastAttack, bestAttack, grammarUseCounts
  appliedMilestones/settlementIds
```

Profile는 로컬 playerId를 키로 하고 표시명·기본설정·문법/룬해금·최고기록·초회가이드플래그·원정별누적요약을 갖는다. **닉네임을 계정 식별자나 보안 장치로 사용하지 않는다.** 공유 태블릿에서 로컬 프로필 생성/전환을 간단히 지원하고 같은 이름으로 기존 기록을 자동 병합하지 않는다. 로그인은 추가하지 않는다.

### 15.2. SentenceSnapshot과 AnalysisResult

```text
SentenceSnapshot
  schemaVersion, sentenceId, orderedTokens[]
  token: cardInstanceId, cardDefId, lexemeId,
         selectionId, surface, allowedFormCandidates, position

AnalysisResult
  schemaVersion, grammarVersion, inputFingerprint
  status, rootNodeId, mainClauseId
  nodes[], clauses[], resolvedTokenRoles[]
  grammarHits[], issues[], evidenceMarks[], ambiguities[]
  coverage: consumedCardIds, issueAffectedCardIds, unlicensedCardIds
  diagnostics: capabilityId/limit/errorId (developer only)
```

Grammar input에는 카드 희귀도·연마 점수·룬 효과·보스 HP를 넣지 않는다. 모든 surface는 registry에서 재검증한다. DOM dataset의 임의 문자열을 유효한 Lexeme로 신뢰하지 않는다.

모든 Node/Hit는 실제 cardInstanceId를 참조한다. 관계절 선행사/명사구 내부 같은 미래 구조를 표현할 `scopeNodeId`, `headCardId`, `connector` 자리를 둔다. 배열 인덱스만 장기 기록하면 재정렬·저장 복원에서 오염되므로 안정적인 ID를 사용한다.

`GrammarHit`에는 score가 없고 `tag, scope, cardIds, validity, evidenceKey`만 둔다. 같은 evidenceKey의 동의 태그 중복은 정규화한다. 불확실한 confidence 0.99 같은 검증 안 된 확률을 만들어내지 않는다.

### 15.3. AttackResolution

```text
AttackResolution
  schemaVersion, attackId, runId, battleId, expectedRevision
  versions: language/grammar/balance/runes/presentation
  sentenceSnapshot
  cardScoringSnapshot     # 강화/앞면분류 등을 공격 당시로 고정
  runeSnapshot            # 당시 순서·레벨
  analysis
  scoreTimeline[]         # 앞/뒤 점수·source/evidence, 하나의 정합된 순서
  preRuneScore, postRuneScore, postRegionScore
  bossEffects[]
  finalPower, actualHpLoss, overkill
  enemyHpBefore, enemyHpAfter, killed
  proposedStateEffects    # discard/turn/killGold, 계산 결과
  visualBasis             # intensity baseline, before/after states; no RNG game effects
```

`actualHpLoss=min(enemyHpBefore, finalPower)`, `enemyHpAfter=max(0,before-finalPower)`, `overkill=max(0,finalPower-before)`를 일관되게 사용한다. 플레이어 최고 공격은 finalPower, 총 실제 피해는 actualHpLoss로 각각 이름을 명확히 한다. 면역이면 finalPower/actualHpLoss 모두0이며 preBossScore는 별도 기록한다.

### 15.4. 제출 처리

1. 상태가 EDIT인지와 문장 비어있지 않음을 검사한다.
2. 제출 즉시 resolving 잠금·중복 commandId 방지. 문장/카드/룬/적/rng revision 스냅샷 생성.
3. 문법 분석 → 상태별 정책. 무효/미지원/엔진오류면 명시적 피드백 후 EDIT로 복귀하며 게임자원은 무변경.
4. Scoring → Rune → Stage/Boss → AttackResolution을 순수 계산한다.
5. 원래 revision/battleId와 일치하는지 검사한다. 지연 결과가 이전 전투에 대한 것이면 폐기한다.
6. RunController가 HP·카드·턴·최소 통계를 **동일 command에 한 번만** 반영한다.
7. Presentation이 스냅샷을 재생한다. 결과는 이미 고정되어 있다.
8. 연출 종료 또는 fallback 뒤 승리/패배/다음턴으로 전환한다. 다음 턴 드로우와 승리 보상은 각각 고유 사건으로 한 번 처리한다.

보상 재화 지급은 BATTLE_VICTORY settlement 단위로 하며 공격피해 함수와 UI callback 양쪽에서 지급하지 않는다. 전투내 해금실적과 보상추첨 순서도 고정한다.

### 15.5. 상태 머신과 에러 경로

LOBBY → SETUP → STAGE_INTRO → BATTLE_READY → EDIT ↔ EXCHANGE_SELECT → RESOLVING → PRESENTING → TURN_START/VICTORY/DEFEAT → REWARD → BETWEEN_BATTLES/CONTENT_COMPLETE.

구현에서 `BATTLE_READY`는 최초 패가 준비된 안전 checkpoint의 이름이다. 편집 입력을 받는 실제 combat.phase는 EDIT로 둘 수 있고, `battleDirty=false && turnIndex=1`일 때만 READY 저장을 허용한다. 최초 입력이 READY 상태에서 거절되거나 EDIT로 전환하자마자 초기 저장 버튼이 사라지는 충돌을 만들지 않는다. 도움말·사전 보기 등 비변경 명령은 dirty로 만들지 않는다.

형태/사전/저장/설정은 modal UI 상태이며 전투 phase를 임의로 다른게임상태로 바꾸지 않는다. RESOLVING/PRESENTING 동안 카드·교환·룬순서·공격·로드 입력을 잠근다. 항상 취소/복구의 소유자를 정한다. Promise가 resolve되지 않아 영원히 멈추는 상태는 허용하지 않는다.

애니메이션 실패는 fast-forward to final view, 저장 실패는 재시도/메모리 플레이 유지, 데이터 로딩 실패는 명확한 시작 오류 화면과 재시도. ‘배경만 보임’은 인수 실패다.

## 16. RNG·수동 저장·개인 기록

### 16.1. 재현성

직렬화 가능한 시드 PRNG 하나의 구현을 쓰되 스트림을 deck/reward/shop/encounter로 파생한다. 알고리즘 버전·각 state/진행위치를 저장한다. `Math.random()`은 게임 규칙 모듈에서 사용하지 않는다. visual RNG는 완전 별도다.

같은 seed만으로 언제나 모든 런이 같다는 과장 금지: 설정·콘텐츠버전·시작해금기준·플레이어선택이 같아야 한다. new runId는 식별용이고 카드/보상 난수의 숨은 seed가 되면 안 된다. `localeCompare`의 환경차이 등으로 후보 순서가 달라지지 않게 안정적인 ID 정렬을 사용한다.

### 16.2. 로컬 저장의 최소 완성

IndexedDB에 로컬 프로필과 원정 3슬롯을 분리한다.[T4] 저장 이름은 앱 전용 namespace를 쓰고 다른 게임의 storage를 clear하지 않는다.

프로필의 최고기록/해금/튜토리얼정보는 결과 사건 단위로 자동 보존한다. 원정 전체의 자동 세이브는 하지 않는다. 매 카드 이동을 저장하지 않는다.

**허용:** 최초 행동 전 BATTLE_READY, 선택지 고정된 REWARD, BETWEEN_BATTLES, CONTENT_COMPLETE.  
**불가:** 카드 이동 이후 전투 도중, 교환/드래그/계산/연출 중. 카드편집 Undo로 원래처럼 보이게 만들었다고 save-lock을 우회하지 않는다. 첫 상태 변경 때 `battleDirty=true`로 관리한다.

로드 시 frozen hand/piles/reward/rng/룬레벨·순서/자원/버전/실적 기준을 그대로 복원한다. 셔플이나 새 보상 생성 함수를 다시 호출하지 않는다. 메뉴를 열고 닫는 것도 RNG를 사용하지 않는다.

### 16.3. 신뢰성

저장 완료 표시는 write request를 보낸 직후가 아니라 트랜잭션 완료 후 한다. 손상된 저장·다른 앱 파일·미래 version·없는 cardDef·중복 ID·음수자원·pile 합계 불일치를 검증한다. 실패하면 기존 슬롯을 지우지 않는다. 현재 플레이를 유지하고 ‘저장하지 못함’을 분명하게 보여 준다.

적어도 현재 version의 검증·복원은 구현하고 미래 migration registry는 작은 자리만 둔다. 임의로 알 수 없는 저장을 강제로 읽어서 카드를 삭제하는 자동복구는 금지한다.

local profile/store export-import는 시간 여유 선택기능이지 필수로 범위를 늘리지 않는다. 미지원이면 없는 기능을 버튼으로 표시하지 않는다. 브라우저 데이터 삭제/기기 변경/다른 origin에서 로컬 기록이 자동 유지된다고 약속하지 않는다.[T4]

### 16.4. 중복 기록과 오래된 슬롯

- 한 runId의 Stage1 클리어는 유효 원정 누적1회다. 동일 저장 재클리어를 반복 계산하지 않는다.
- 같은 attackId를 최근공격 재생해서 도감 횟수가 증가하지 않는다.
- 샌드박스·합성 연출 데이터·디버그 조작은 실적에 들어가지 않는다.
- 진행 중 원정은 시작시점 해금기준+자신의 성취만 사용한다. 다른 저장 슬롯에서 생긴 해금을 소급 가져와 frozen offer를 바꾸지 않는다.
- 로컬 기록은 플레이어 편의를 위한 것이며 보안 검증된 공식 랭킹 기록이라고 표시하지 않는다.

### 16.5. 0.1 오프라인의 정확한 범위

**필수:** 초기 필수 자원이 모두 로드된 뒤 인터넷을 끊어도 현재 원정·새 전투·사전·효과·로컬 저장이 동작한다. 런타임 핵심 코드/데이터를 이후 전투에서 원격 lazy-load하지 않는다.

**이번 범위 아님:** 처음 접속 자체가 오프라인인 경우, 탭/브라우저를 닫았다가 네트워크 없이 재실행, 앱 설치. 이는 PWA/캐시 수명·버전교체 테스트를 포함한 후속 작업이다.[T7] 브라우저 HTTP 캐시가 우연히 작동했다는 이유로 ‘완전 오프라인 설치 지원’이라고 보고하지 않는다. 기존 다른 앱의 Service Worker를 등록해 재사용하지 않는다.

## 17. 문장 샌드박스

학생 전투와 같은 Grammar/Score/Rune 모듈을 사용하는 개발 전용 화면이다. 학생의 첫 화면을 JSON 콘솔로 만들지 않는다.

- 현재 registry의 카드 목록에서 선택·복사, 형태·순서 조절.
- 명시적 분석 버튼. 자동 분석은 debug 토글로만 가능하고 일반 전투에 영향을 주지 않는다.
- 결과: 분석 상태, 주절 Frame, Node/Hit/Issue, 카드 범위, 점수 타임라인, 룬 전후, finalPower.
- fixture를 골라 같은 카드 ID/선택형으로 재현하고 입력/결과 JSON을 내려받는다.
- Grammar fixtures와 Presentation-only fixtures를 구분한다. 관계절 연출 데이터로 그림이 나왔다고 ‘관계절 엔진 지원’이라고 하지 않는다.
- 정상 제출 입력은 Card ID 기반. 편의용 문자열 입력을 만들 경우 registry로 해석 가능한 단어만 변환하며 동음/다품사 후보는 확인한다. 자유 문자열을 그대로 완전문장 취급하는 우회 금지.
- RNG/턴/pile 경계 테스트는 개발도구로 제공할 수 있으나 일반 진행의 점수·해금에 기록하지 않는다.
- 단위 테스트와 UI가 서로 다른 모의 점수 계산기를 사용하지 않는다.

## 18. Work 실제 수행 단계

### Gate A — 골격과 계약

새 폴더·모듈 경계·JSDoc 타입·읽기전용 registry·config 로더·ID validator·시드 RNG·기본 테스트를 작성한다. `npm ci/test/build` 경로를 마련한다. 데이터 schema만 만들고 종료하지 않는다.

**완료 기준:** 작은 실데이터로 문장 카드 스냅샷을 받아 분석·점수 기록 형식을 반환할 수 있고 DOM/Firebase 의존이 없다. progress에 파일·테스트 상태를 기록한다.

### Gate B — 실제 언어 데이터와 샌드박스

선정 어휘의 언어 데이터를 작성하고 기본 Phrase/Clause Matcher와 bounded diagnostics를 구현한다. 긍정·오류·미지원 테스트, 동형형태·수식·PP를 검증한다. 화면의 카드 조작/형태 선택으로 결과를 확인한다.

**완료 기준:** 외운 문장뿐 아니라 조합된 새 문장에 같은 규칙을 적용하고, 틀린 문장을 표면 길이로 맞다고 하지 않는다. 수동 로그/스크린샷+자동테스트 증거를 남긴다.

### Gate C — 한 전투의 완성

30장덱·첫패·교환·준비·6턴·최종피해·카드 이동과 기본이모지/타격을 연결한다. 상태원자성과 마지막턴 승리·중복클릭·드로우 고갈을 먼저 확인한다. 부드러운 입력·제출 후 점수리듬·효과음도 여기서 만든다.

### Gate D — Stage1 세 전투와 룬·보상

초회 튜토리얼, 첫룬 고정/다회차랜덤, 초기10룬, 연마/제거/건너뛰기, 지역보스와 내용완료를 연결한다. 같은 게임을 최소 여러 seed와 네 어휘모드로 실행한다.

### Gate E — 저장·배포·최종검증

로컬 프로필/수동3슬롯, 오류경로, 기기레이아웃, production build/서브경로, 인터넷 차단 후 계속하기, 재시도를 검증한다. source ZIP과 dist-only ZIP을 생성한다.

**각 Gate는 중간 검증 단위이지 작업을 여기서 멈추고 사용자 승인을 계속 요구하라는 뜻이 아니다.** 명세에 필요한 선택은 여기의 기본값으로 진행한다. 진짜 접근권한/필수자료 부재가 있으면 그 의존부분만 표시하고 독립 작업을 계속한다. 중단되면 현재 코드와 `PROGRESS.md`/`NEXT_STEPS.md`를 보존하여 이미 통과한 부분을 처음부터 재작성하지 않게 한다.

## 19. 인수 테스트와 검증 증거

`05_ACCEPTANCE_CASES_v0_1.json`은 필수 대표 사례이며 **실행 결과가 아니다.** Work는 실제 모듈에 연결해 테스트하고 결과를 새로 제출한다.

### 19.1. 언어·정규화

정상 현재형/SV/SVC/SVO, 명사구/관사/복수/대명사/수식/기본PP를 검사한다. 올바른 사례의 단어를 다른 동일 Frame 후보로 바꾼 생성문도 시험한다. 목록에 없는 조합이라도 같은 규칙이면 성공해야 한다.

음성·전공 의미판단 없이도 확인되는 오류는 확실하게 잡는다. 어순을 바꾼 일부 테스트가 우연히 다른 정상 문장이 될 수 있으므로 ‘모든 순열=오류’로 가정하지 않는다.

### 19.2. 점수·룬

- 표의 I run/She is happy/I like dogs/She like dogs 점수.
- 완성+루비+호박 순서: 40→60→84→105→지역131.
- 완성+호박: 지역후93, 호박+완성: 지역후87.
- very 3장의 개별 실물카드만 부사 룬3회, 같은 파싱후보중복은0회추가.
- 연마가 기본과 enhancement에서 두 번 계산되지 않음.
- Lv3같은룬 보상제외, Lv1중복획득Lv2, 슬롯만석취소 무손실.
- 운영 룬은 규칙 초기 스냅샷에서 한 번, 룬 이동/사전/저장으로 재지급 없음.

### 19.3. 덱·턴·상태

모든 action 후 active=piles합집합/중복없음, hand≤한도, sentence≤16, 턴/교환/재화≥0을 확인한다. 최초드로우6 not9, 첫턴+3없음, 한장교환과전체교환 모두횟수1, 빈교환0, 부족Draw재셔플, both-empty정상, 가득찬손패회수/맞교환, 마지막턴승리우선, 무효문장불소모, 정상0피해공격소모(미래 fixture)를 시험한다.

### 19.4. 생성 접근성

네 어휘모드 각각 seed **2,500개(총10,000개)**의 시작덱/초기패 구조검사를 개발 스크립트로 실행한다. 모든 seed에서 30장과 1·2·3형식 경로, 초기패 한 개 이상의 정상경로를 검사하고 보정률·fallback률을 보고한다. 같은 Parser를 사용한 자기검사만으로 언어정확성이 증명된다고 말하지 말고 수작업 정답 테스트도 병행한다.

이 검사는 전체 전투승률 테스트와 다르다. 별도로 최소 몇 seed에 대해 실제 draw/교환/공격 sequence를 로그로 끝까지 실행한다. 단순 테스트 policy로 클리어가 안 된 seed가 곧 게임 불가능의 증거는 아니므로 후보 탐색 한계/플레이전략/데이터실패를 분리해서 보고한다. **‘I run을 매턴 준다’는 fixture로 전체 접근성이 검증됐다고 하지 않는다.**

### 19.5. UI·성능·복구

- 지정 네 viewport에서 로비·편집·형태메뉴·교환선택·룬선택·점수연쇄·피격·결과·저장·도감의 캡처.
- mouse/touch emulation + 실제 가능한 브라우저에서 클릭/드래그/터치가 동작하는지. WebKit headless 결과를 실제 iPad 검사라고 주장하지 않는다.
- 클릭·드래그·제출 피드백 목표 약100ms, 실제 p50/p95 보고. 저사양·터치에서 뭉개지면 애니메이션 비용부터 줄인다.
- 문법점수 노출 전 없음, 룬 설명과 실제수치일치, 태블릿글씨/10손패/16조합 가독성, effectsOff에도 진행가능.
- AudioContext 거부/이미지없음/탭전환/resize/빠른이중클릭/저장실패/깨진슬롯에서 입력무한잠금·배경만남음 없음.
- dist build를 임의 서브폴더로 올린 local static server에서 JS/CSS/자산경로/새로고침 검사.
- 모든 초기필수자원 로드 후 network offline으로 전환하고 Stage1 끝까지/로컬저장 계속하기.

### 19.6. 보고의 정직성

`PASS / FAIL / NOT RUN / OUT OF SCOPE`를 구분한다. 파서미구현/테스트못돌림을 PASS로 바꾸지 않는다. 테스트파일 수나 화면캡처수만으로 게임완성도를 주장하지 않는다. 환경제약이 있으면 정확히 무엇을 실행하지 못했는지와 남은 검증을 기록한다.

## 20. 배포와 사용자가 할 일 최소화

### 20.1. 원본과 배포본은 분리

Vite가 원본 모듈들을 정적 dist로 빌드한다.[T1] 사용자가 각 엔진 파일을 따로 빌드하거나 Firebase에 업로드할 필요가 없도록 한다.

**필수 결과물 A:** `SentenceBalatro_0.1_source.zip` — src/data/tests/docs/package files/lockfile. node_modules 제외.  
**필수 결과물 B:** `SentenceBalatro_0.1_deploy.zip` — ZIP 최상단에 index.html, assets, .nojekyll, 배포 안내. source 구조를 배포본처럼 주지 않는다.

원본 index.html이나 dist/index.html 하나만 복사하면 나머지 파일이 없어 실패한다. 배포 안내에는 **‘배포 ZIP을 풀고 내용 전체를 올린다’**를 명시한다.

### 20.2. 사용자 기본 배포 경로

0.1은 기존 다른 게임을 덮어쓰지 않는 새 GitHub Pages 저장소/폴더에 deploy ZIP 내용 전체를 업로드하는 절차를 기본 안내로 제공한다. 계정이나 실제 repo를 이 작업에서 자동 생성/게시하지 않는다.

Vite `base:'./'`와 동일 base를 참조하는 자산 해석, hash 기반 view(또는 단일 루트 view)를 사용해 임의 프로젝트 하위 경로에서 동작하도록 검증한다.[T1] `/assets/...`를 임의의 절대경로로 박아 넣지 않는다. public asset 경로도 resolver를 통한다.

GitHub Pages의 실제 게시 위치에는 index.html이 최상위에 있어야 한다. 정적 사전빌드 배포에 `.nojekyll`을 함께 제공한다.[T2] README에는 GitHub Pages 설정 위치·업로드대상·올바른/잘못된폴더 예시를 간단하게 적는다. 이 문서에서 아직 알 수 없는 실제 URL을 만들어내지 않는다.

### 20.3. 개발용 명령

원본에는 사용한 Node 버전과 아래 스크립트가 있어야 한다.

```text
npm ci
npm run dev
npm test
npm run validate:data
npm run test:e2e
npm run test:decks
npm run build
npm run preview
npm run package
```

`preview`는 local production build 검사 용도이지 실제 공개 서버가 아니다.[T1] 사용자는 deploy ZIP으로 공개할 때 Node 명령을 직접 사용할 필요가 없게 한다. 로컬 파일 더블클릭 `file://` 지원은 보장하지 않는다. `file://`로 열면 백화면 대신 ‘정적 서버/GitHub Pages에서 실행’ 안내를 가능하면 제공한다.

GitHub Actions 자동배포는 후속 편의기능으로 두고 0.1에서 두 개의 배포방식을 필수 학습으로 강요하지 않는다. 필요한 경우 예제 workflow는 별도 문서에만 준비한다.

### 20.4. 보안·개인정보

이름/저장metadata/사전데이터는 textContent 등 안전한 텍스트로 표시한다. 임의 HTML 삽입하지 않는다. 개인정보·실제 학생명/기록을 샘플 데이터나 public repo에 포함하지 않는다. 외부 수집/분석 SDK 없음. 비밀키·Firebase admin credential·토큰을 src 또는 deploy에 넣지 않는다.

로컬 기록은 같은 기기의 다른 사람이 접근할 수 있는 편의프로필이며 비밀번호 보호 계정이 아니다. 여러 기기 동기화·정식 서버랭킹은 이번 범위 밖이다.

## 21. 납품물과 완료 판정

### 21.1. 필수 납품 파일

다만 명시적으로 후속에 둔 48전투·상점·PWA·Firebase가 없다는 것은 0.1 결함이 아니다. 화면과 보고서에서 그 경계를 정확히 알려야 한다.

## 22. 운영자가 처음 해 볼 인수 시나리오

1. 새 로컬 프로필로 이름입력, 초급/여행자/난이도1 시작. 받은 패에서 스스로 한 문장 조립.

4. 두 카드 동시 교환 → 카드수만큼 받음, 횟수1만 차감, 턴보존.
5. 문장을 보관하고 준비 → 다음턴3장, 남은턴1감소.

9. 안전지점 수동저장→로드: 카드·룬·보상·난수 같음. 같은저장클리어 반복은 원정실적중복없음.

12. network 차단 후 현재앱으로 전투계속·로컬저장. 오프라인 재시작은 0.1미지원 설명 확인.

테스터에게 코드를 읽게 하지 말고 이 행동만으로 기본 성공 여부를 확인할 수 있게 한다.
